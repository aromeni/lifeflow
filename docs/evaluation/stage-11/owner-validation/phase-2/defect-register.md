## Environmental artefacts ruled out (not defects, not test-script bugs)

- **Functional E2E suite (`./scripts/e2e.sh`) failed twice on rate-limiting-dependent tests** (`demo-approvals.spec.ts`, `rate-limiting.spec.ts` Journey C) during this phase's gate-list re-verification. Root cause: this session ran an unusually large number of local suites back-to-back (design suite ×5, resilience suite ×5+, rollback rehearsal ×3, backup/restore rehearsal ×3, owner walkthrough ×3, the full backend suite) all sharing the same default dev Redis instance (`redis://localhost:6380/0`, per `.env.example`) with nothing between them ever flushing it — so rate-limit buckets that specific tests expect to start at a known, small test-only capacity had already been partially consumed by unrelated earlier activity in the same session. `docker compose exec redis redis-cli -n 0 FLUSHDB` followed by a clean re-run reproduced 10/10 passes. This is an artefact of this session's own extraordinarily long, many-suite local testing sequence — a normal CI run (fresh service containers every job) or a normal single-suite developer workflow would never hit it. Not a product defect, not a test-script defect (the tests correctly assume a clean rate-limit budget, which is a reasonable assumption for both CI and normal local use).
- **Local resilience-suite re-verification run 1 of 5 failed to start its web dev server** — see T-P2-1 above; same root cause (leftover local process state from this session's own unusually long sequence of runs), different symptom.

## Non-defects explicitly considered and ruled out

- **Calendar uncertain-write path not separately screenshotted in the manual walkthrough** — `e2e_google_support.py`'s existing seed helpers (`seed-account`, `seed-draft-source`) only seed a Gmail-sourced scheduling item; there is no calendar-event seed helper. Rather than extend shared test-support infrastructure for one screenshot, the walkthrough documents that the Calendar path renders through the identical `execution-result` component and copy the Gmail screenshot already shows, while its distinct backend mechanism (`GoogleCalendarEventExecutor`) is proven automatically and repeatedly (10 cycles) by `test_stage11a_phase2_uncertain_write_repeatability.py`. Not a coverage gap — a deliberate, disclosed scoping decision.
- **"Timeout before write acceptance" collapses to the same `uncertain` outcome as "accepted but unconfirmed" in the real executor code** — initially expected these to be two distinguishable *outcomes* per the governing task's framing. Reading `action_executors.py` directly showed the product deliberately does not attempt to distinguish them for the write call itself (any transient failure touching the actual write network call is conservatively classified `uncertain`, never silently retried) — the real, tested distinction is instead "refused before any provider call was attempted at all" (`FinalExecutionError`, disclosed, `failed`) versus "the call was made and something about it could not be confirmed" (`uncertain`). Documented precisely in `docs/delivery/stage-11a-phase-2-plan.md`'s failure taxonomy and exercised as such in `test_stage11a_phase2_uncertain_write_repeatability.py`'s two test functions. Not a defect — a safety-positive design choice (never guess that an ambiguous write definitely didn't happen).
- **arq's cron in-progress-key TTL self-heal has no new dedicated automated test** — this is third-party library internal behaviour (`arq==0.28.0`'s `worker.py::_start_job`), not LifeFlow application code. Writing a unit test against a pinned dependency's private scheduling internals was judged low-value and high-maintenance-risk; instead this phase independently re-read and confirmed the exact mechanism against the installed source, byte-for-byte consistent with the existing `worker-recovery.md` runbook's description. See the acceptance matrix's S11A-P2-012 method note.
