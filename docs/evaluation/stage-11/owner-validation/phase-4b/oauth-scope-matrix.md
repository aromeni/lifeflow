## Sign-in scope (separate flow, never combined with the scopes below)

`openid email profile` (`auth.py:32`) — standard OIDC identity scopes, not sensitive/restricted, used only to authenticate a LifeFlow session. Out of scope for this matrix, which covers the four **connector** scopes below.

## Explicit reconfirmations (per governing instruction §6)

- **LifeFlow cannot send Gmail messages.** No code path constructs a request to `/messages/send` or `/drafts/send`; `gmail.compose`'s technical ability to send is not exercised anywhere in `GmailDraftClient`. A new structural test (S11A-P4B-023 companion, added this phase) makes this a standing regression guard rather than a one-time inspection finding.
- **LifeFlow cannot modify or delete an existing Calendar event.** No `update`/`patch`/`delete` method exists in `CalendarEventClient`; a new structural test (S11A-P4B-024) makes this a standing regression guard.
- **Broad provider capability does not override LifeFlow's closed action model.** Both `gmail.compose` and `calendar.events` grant Google-side capability broader than LifeFlow ever exercises. The application's own allowlists and method surfaces — not the OAuth scope — are what actually bound LifeFlow's behaviour, and this is proven by structural tests rather than asserted by documentation alone.

## Rejected scopes

No scope beyond the four above is requested anywhere in the codebase (confirmed by grep across `google_scopes.py`, `.env.example`, and all Google client/route modules). In particular, `gmail.modify`, `gmail.insert`, `gmail.settings.*`, `https://mail.google.com/`, and any full-access Calendar scope are all absent — none is tied to an implemented, approved operation, so none is requested "because it may be useful later."
