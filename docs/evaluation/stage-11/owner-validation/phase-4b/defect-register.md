## P2 findings — found and fixed this phase

- **Denied/cancelled Google consent left stale pending OAuth state and was mislabeled.** Both the sign-in (`auth.py`) and connector-consent (`connected_accounts.py`) callbacks previously fell into the generic `missing_code` branch on a Google-side denial (`?error=access_denied`, no `code`), never calling `consume_oauth_flow`, so the pending flow was never cleared until its 600-second TTL lapsed. **Fixed**: both routes now check `error` first, clear the pending flow via a new `clear_pending_oauth_flow()` helper, and redirect with a distinct `auth_error=access_denied`/`connect_error=access_denied` (the raw Google `error` value is never reflected into the redirect). Verified by two new tests. See [oauth-state-and-binding-results.md](oauth-state-and-binding-results.md).
- **Three production-startup guards had no direct test asserting their specific error.** `SESSION_SECRET must be set in production`, `GOOGLE_OAUTH_ENABLED=true requires <missing fields>`, and `GOOGLE_OAUTH_ENABLED=true requires TOKEN_KEY` were all already-working guards exercised only as unasserted side effects of unrelated test setup. **Fixed**: three new tests assert each guard's specific error message directly. See [provider-production-guard-results.md](provider-production-guard-results.md).
- **Three OAuth-callback edge cases had no test coverage**, though the underlying mechanism already handled them safely: replay of an already-consumed callback, callback after logout, and malformed (`empty`/duplicated) `state` parameters. **Fixed**: three new tests confirm each is handled safely with no code change required. See [oauth-state-and-binding-results.md](oauth-state-and-binding-results.md).

## Test-script defects — found and fixed before this rehearsal was ever reported as passing

Both were bugs in `stage11a_phase4b_connection_rehearsal.py` (this phase's new dry-run script), not in product code, matching the same class of finding as Phase 3's T-P3-1 and Phase 4A's D-P4A-01 — caught by running the tooling rather than assuming it worked.

- **The rehearsal's first draft made a real network attempt against Google's live Gmail API.** Only `app.state.google_oauth_client` was replaced with a mock transport; `app.state.gmail_client`/`app.state.calendar_client` were left pointed at the real, shared `google_http_client` `create_app()` wires by default, and the step-12 read-smoke-test issued `GET https://gmail.googleapis.com/gmail/v1/users/me/messages` with a fake bearer token, receiving a genuine HTTP `401`. **Classification: UNINTENDED UNAUTHENTICATED OUTBOUND ATTEMPT — NO CREDENTIAL OR USER DATA TRANSMITTED; NO SUCCESSFUL GOOGLE API INTERACTION** — a real TCP/TLS connection and HTTP exchange did occur (a `401` cannot be received otherwise), but no genuine client ID/secret/token/session cookie/account identifier/user content was ever sent (the bearer value was a local placeholder string, and the query parameters were a computed date range, nothing else), Google rejected it as unauthenticated, and no provider-side object or state could have been created (the call was a read-only `GET`). See [dry-run-results.md](dry-run-results.md)'s full exact-boundary classification table. **Fixed** two ways: (1) both clients are now also assigned mock-transport-backed instances, matching the exact pattern `test_google_route_integration.py`'s `_app_client` already uses; (2) a new durable safety net (`lifeflow_api.testing.no_live_network.block_live_google_network`) now replaces `app.state.google_http_client`'s transport with a loopback-only guard *before* the mock overrides are applied, so even a future edit that forgets one of the three overrides is refused before any socket opens, rather than silently reaching a real host again — see [dry-run-results.md](dry-run-results.md)'s "No-live-network guard" section and `test_stage11a_phase4b_no_live_network_guard.py` (12 tests). Neither the original attempt nor this fix ever appeared in a commit or a reported-passing rehearsal.
- **Incorrect assumption that full-account deletion physically removes the `User` row.** Reading `account_deletion.py` showed the design is a tombstone (`user.account_state = UserAccountState.deleted`), not row removal — consistent with the existing Phase 4A test (`test_full_account_deletion_removes_key_id_columns_with_the_row`), which only ever asserted `ConnectedAccount` removal, not `User` removal. **Fixed**: the rehearsal's final assertion now checks `account_state` and `ConnectedAccount` absence, matching actual, already-correct product behaviour.

## P2 findings — closed during the Stage 11A Phase 4C integrity check (correcting an inspection error)

- **"No PKCE on the connector-consent OAuth flow" was factually wrong — PKCE was already present the entire time.** This finding was originally recorded, then twice revalidated (against Google's documentation and the wider OAuth security-practice landscape) without ever re-checking its own premise against LifeFlow's actual code. During the Stage 11A Phase 4C integrity check, direct inspection of `oauth_state.py::begin_oauth_flow` — the single function shared by both the OIDC sign-in and connector-consent flows since Stage 7 (`07bb328`, unchanged by Phase 4B) — showed it unconditionally generates a PKCE pair and stores `code_verifier` in the session for every flow, regardless of purpose; `connected_accounts.py::connect_google` passes `code_challenge=pkce.challenge` to `build_authorization_url`, which unconditionally embeds `code_challenge`/`code_challenge_method=S256` (`google/oauth.py:78-92`, `code_challenge` is a required, non-optional parameter); and the connector callback exchanges the code with `code_verifier=flow.code_verifier` (`connected_accounts.py:137`), exactly like the sign-in callback. The original Stage 7 ADR (0003 D28) and completion report (`stage-07.md`) both correctly describe PKCE as shared by both flows — only the OIDC `nonce` is sign-in-only. **Closure**: a new regression test, `test_connector_connect_redirect_also_carries_pkce` (`test_google_auth_and_connections_api.py`), asserts `code_challenge`/`code_challenge_method=S256` on the connector `/connect` redirect, closing the coverage gap that let this documentation error go unchallenged for two phases. **Current state: CLOSED — no code change was needed; the flow was already correct.** See [redirect-uri-and-origin-plan.md](redirect-uri-and-origin-plan.md) and `docs/security/threat-model.md` (T11), both corrected alongside this entry.
- **Google's Testing-status consent-screen publishing issues refresh tokens that expire after 7 days**, and caps test users at 100 — verified against current official Google documentation (Google Cloud Console Help — Manage App Audience, `support.google.com/cloud/answer/15549945`), re-checked and re-quoted directly during this correction task, dated 2026-08-01. This is a real, load-bearing constraint on the eventual 14–30 day soak period (a single consent will not survive it without re-consent roughly every 7 days, or publishing to production — which triggers restricted-scope verification and an annual security assessment for the two Gmail scopes). **Closure condition**: an explicit owner decision between Option A (Testing-status re-authorisation cadence) and Option B (a separately-reviewed publishing-status change) — see the dedicated [soak-period-decision.md](soak-period-decision.md), which documents both options in full without choosing either — made before the soak period begins (Phase 4C, out of scope for this task). **Why this doesn't block Phase 4B**: Phase 4B is readiness and planning only; it does not begin the soak period, and the constraint is honestly documented rather than solved or hidden. See [google-platform-requirements.md](google-platform-requirements.md).

## Non-defects explicitly considered and ruled out

- **Concurrent-callback handling** — not proven safe or unsafe by a dedicated test this phase (would require firing two simultaneous requests with an identical valid session cookie and state value, a narrow window with no demonstrated benign trigger). Recorded honestly as an open question in [oauth-state-and-binding-results.md](oauth-state-and-binding-results.md) rather than fabricated as either proven-safe or a defect.
- **Demo mode's `/demo/start` route has no production guard of its own** — considered and ruled out as a gap distinct from the six conditions the governing instruction's §23 lists, since it requires an authenticated session, only ever writes to the calling user's own account, uses no OAuth credential, and is unrelated to the real-provider pathway those six guards protect. Not a Phase 4B connection-readiness concern.
