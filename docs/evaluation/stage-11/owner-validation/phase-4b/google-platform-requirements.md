| Requirement | Official source | Exact requirement | Applies during disposable owner-only testing? | Relevant only for external/production users? |
|---|---|---|---|---|
| OAuth consent-screen publishing status | [Google Cloud Console Help — Manage App Audience](https://support.google.com/cloud/answer/15549945) | A project's OAuth consent screen has a publishing status of **Testing** or **In production** | **Applies** — the project will be created and kept on **Testing** for this entire testing programme | Publishing to production is a future/external-user concern only |
| Testing-status test-user cap | Google Cloud Console Help (Manage App Audience / OAuth App Verification Help) | **Testing** status permits at most 100 listed test users; only listed test users can complete consent | **Applies**, trivially — exactly 2 accounts (A, B) will ever be listed, far under the cap | N/A |
| Testing-status refresh-token expiry | [Google Cloud Console Help — Manage App Audience](https://support.google.com/cloud/answer/15549945?hl=en), re-verified 2026-08-01, exact quote: *"Authorizations by a test user will expire seven days from the time of consent. If your OAuth client requests an `offline` access type and receives a refresh token, that token will also expire."* (re-confirmed against this same official page for this correction, superseding the earlier citation's reliance on secondary community write-ups) | An **External** user-type app in **Testing** status issues refresh tokens that expire **7 days** after consent; the corresponding authorization also expires 7 days after consent | **Applies directly** — this is a **hard, load-bearing constraint on any future soak period**: a 14–30 day soak cannot run on a single Testing-status consent without a re-consent step roughly every 7 days, or without publishing to production (which triggers verification, see below). **This phase records the constraint and does not resolve it** — resolving it (Option A: Testing-status re-authorisation cadence, vs. Option B: a separately-reviewed publishing-status change) is an explicit future Phase 4C/soak-period owner decision — see [soak-period-decision.md](soak-period-decision.md) | Once published to production and verified, refresh tokens no longer expire on this 7-day cycle |
| Verification exemption for Testing status | [Google — Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) | "If your app is in the development, testing, or staging phases, verification isn't required." Testing-status apps remain subject to the user cap and an unverified-app warning screen shown to test users | **Applies** — no verification is required or attempted for Phase 4B or the eventual owner-only soak period, as long as consent-screen status remains Testing | Verification only becomes required to publish to production / serve users beyond the test-user list |
| Gmail scope classification | [Google — Gmail API OAuth scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) | `gmail.readonly` and `gmail.compose` (the two Gmail scopes LifeFlow requests) are both classified **RESTRICTED** — restricted scopes require OAuth app verification plus an annual third-party security assessment **before production use** | Testing-status exemption above applies — no verification/assessment required while Testing | Verification + annual CASA/App-Defense-Alliance security assessment become required only for production publishing with restricted scopes |
| Calendar scope classification | [Google Cloud Console Help — Restricted Scopes](https://support.google.com/cloud/answer/13464325); [Sensitive scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification) | `calendar.readonly` and `calendar.events` (the two Calendar scopes LifeFlow requests) are classified **SENSITIVE** (a lighter tier than restricted) — sensitive scopes require standard OAuth verification for production, not the additional security assessment | Testing-status exemption applies | Standard verification only becomes required for production publishing |
| Redirect URI scheme | [Google — Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server) | Redirect URIs must use HTTPS, except `localhost`/loopback URIs, which are explicitly exempted for development/testing | **Applies** — the current configured values (`http://localhost:8010/auth/google/callback`, `http://localhost:8010/connected-accounts/google/callback`) are compliant as-is for local owner-only testing | A future non-local deployment (Stage 12+) would require HTTPS redirect URIs; not applicable here |
| Redirect URI exact-match / no wildcard | Google — same source as above | Registered redirect URIs must exactly match the value sent at authorization and token-exchange time; no wildcard hosts | **Applies** — LifeFlow already sends a single fixed configured value at both stages (`auth.py:110,140`; `connected_accounts.py:90,124`), so this is satisfied by construction, not by new work |
| Token/refresh-token behaviour and revocation | [Google — OAuth 2.0 Policies](https://developers.google.com/identity/protocols/oauth2/policies) (general reference); community-confirmed Testing-status behaviour above | Refresh tokens can be revoked by the user (Google Account settings), by Google (inactivity, security event), or expire per the Testing-status 7-day rule above; a revoked/expired refresh token yields `invalid_grant` on the next refresh attempt | **Applies** — LifeFlow's existing `InvalidGrantError` handling (`accounts.py:327-343`, marks the account `revoked`, requires re-authorisation) is the correct, already-implemented response to any of these causes; Phase 4B does not need to distinguish *why* a refresh failed, only that it fails safely, which is already tested |
| API enablement (Gmail API, Calendar API) | Google Cloud Console (project-level API Library) | The Gmail API and Google Calendar API must each be explicitly enabled on the dedicated Google Cloud project before any OAuth client on that project can call them | **Applies** — required once the project is created (Phase 4B does not create it); recorded as a checklist item in [google-cloud-project-plan.md](google-cloud-project-plan.md) |
