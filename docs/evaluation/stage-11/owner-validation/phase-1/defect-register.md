## F-002 closure addendum (2026-07-31)

F-002 was originally mitigated (baselines regenerated) but left root-cause-open, with an explicit note that "baseline drift itself not fixed at the root — it will resurface again after enough further real time passes." A follow-up closure task fixed the root cause before PR #10 merged. See the updated register row below (status changed from "mitigated, not root-caused" to **CLOSED — ROOT CAUSE FIXED**) and [f-002-closure-acceptance-matrix.md](f-002-closure-acceptance-matrix.md) for the full 24-row verification trail. Summary:

- **Prior symptom:** two visual-regression baselines (Today, Approvals: Gmail draft card) periodically failed on genuine content differences as real time passed.
- **Causal mechanism:** `demo_mode.py`'s `start_demo` route derived the synthetic dataset's materialisation anchor from `datetime.now(ZoneInfo(user.timezone))` — the real host clock — on every `/demo/start` call. `SyntheticEmailConnector`/`SyntheticCalendarConnector` (`connectors/synthetic.py`) resolve every fixture's `day_offset` against that anchor, so which fictional item fell in-window and ranked highest drifted as real time passed.
- **Permanent fix:** a new `demo_clock_override` setting (`config.py`), gated behind the pre-existing `e2e_test_controls_enabled` flag exactly like `google_api_origin_override` (Stage 9 Phase 5 §20's established test-control pattern). `demo_mode._resolve_now()` uses it in place of the host clock only when both are set; nothing else in the app ever reads it.
- **Production safety boundary:** the existing `e2e_test_controls_enabled`-in-production startup guard (`main.py:103-104`) covers the new field automatically since it gates on the flag alone, not on which override is populated — extended test coverage confirms this explicitly (`test_e2e_test_controls_enabled_refuses_to_start_in_production_with_demo_clock_override`, `test_demo_clock_override_alone_is_safe_in_production`). No route reads `demo_clock_override` from request input, so no client can influence server time.
- **Regression proof:** `apps/api/tests/test_stage11a_demo_clock_determinism.py` — the override branch never calls `datetime.now()` at all (proven via a monkeypatched `datetime` subclass that raises `AssertionError` if reached), including at midnight/month/year boundaries; the override is inert unless the flag is also on; two independent synthetic users import byte-identical content under the same override; action-proposal expiry (`action_proposal_service.py`'s own `_now` factory, structurally independent of `demo_mode.py`) keeps anchoring to the real wall clock even with a far-past override active. `apps/web/playwright.design.config.ts`'s API `webServer` entry now sets `E2E_TEST_CONTROLS_ENABLED=true` / `DEMO_CLOCK_OVERRIDE=2026-03-15T09:00:00+00:00`.
- **Final baseline source environment:** Darwin baselines regenerated locally via `--update-snapshots` against the fixed clock (2 of 8 files changed, matching the original diagnosis); Linux baselines regenerated on real Linux/Chromium GitHub Actions CI via the same disposable, branch-scoped, no-services-block temporary workflow pattern used for the original mitigation, downloaded and visually confirmed (SHA256-diffed against the previously committed files — same 2 of 8 changed) before being committed and the temporary workflow removed.
- **Stress-tested:** 5 consecutive full local design-suite passes, 3 consecutive visual-regression-only passes, and one pass with the API launched under `TZ=Pacific/Kiritimati` (UTC+14) — all against the same committed baselines, no regeneration between runs, confirming host timezone cannot affect content. (Host *date* independence is proven at the stronger, unit-test level via the exploding-`datetime.now()` mechanism above, rather than by an environment-level simulation — the code path under test never reads the host clock in the override branch, which the test enforces directly.)
- **Unrelated flake found and fixed during stress-testing:** running the full design suite repeatedly (not something the original Phase 1 or F-002 mitigation had done) surfaced a pre-existing, load-dependent hydration race in `accessibility.spec.ts`'s keyboard-only landing-page test — pressing Enter before React finished hydrating the "Try demo" button's `onClick` handler under CPU contention from prior tests. Fixed with an explicit `page.waitForLoadState("networkidle")` before the tab-key loop; confirmed stable across all 5 stress-test runs afterward. Not a product defect (server-rendered HTML was correct throughout; only the test's timing assumption was wrong) and not logged as a new register row for that reason, consistent with this register's existing convention for test-only issues (see "Non-defects" below).

## Non-defects explicitly considered and ruled out

- **Audit History screenshot timing** — the first walkthrough run screenshotted the page mid-load. This was a defect in the **new test script**, not the product (the existing `e2e/audit-history.spec.ts` already waits correctly and was never affected). Fixed in the script; not logged as a product defect. See [execution-log.md](execution-log.md).
- **Imported-data deletion "unavailable" for demo sessions** — initially looked like a possible gap (S11A-P1-018) until the UI's own copy ("Connect and sync an account to enable imported-data deletion") and the component logic (`DeletionControls.tsx:337-357`, gated on `googleAccountId`) confirmed this is intentional, accurate scoping: a synthetic demo account has no real external provider relationship to separately disconnect-then-clean-up, and full account deletion already covers its data. Not a defect.
- **`.local` email domain rejected by `EmailStr`** — surfaced while building the reset-repeatability harness (`dev-login` returned 422 for an explicitly-supplied `...@lifeflow.local` address). This is `email-validator` correctly rejecting a reserved-use TLD when validation actually runs; the pre-existing `dev@lifeflow.local` default only works because Pydantic v2 doesn't validate field defaults. Not a product defect — worked around by using `.example` for all new synthetic identities (see [synthetic-data-inventory.md](synthetic-data-inventory.md)).
- **Landing-page hydration race under full-suite load** — surfaced while stress-testing the F-002 fix (5 consecutive full design-suite runs). A pre-existing test-timing gap (interacting with the "Try demo" button's keyboard focus before React finished hydrating its click handler), not a product defect — the server-rendered HTML was correct the whole time. Fixed in `accessibility.spec.ts` with an explicit `waitForLoadState("networkidle")`.
