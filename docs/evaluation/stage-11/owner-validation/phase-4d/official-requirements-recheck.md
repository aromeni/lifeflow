# Stage 11A Phase 4D — Official Google Requirements Recheck

**Status:** Rechecked against current official sources · **Date checked:** 2026-08-04

This recheck supplements, and does not erase, [Phase 4B's platform requirements](../phase-4b/google-platform-requirements.md) and [Phase 4C's recheck](../phase-4c/official-requirements-recheck.md). Only official Google documentation is used. No requirement here expands the authorised scope set.

|---|---|---|---|---|
| Web-server authorization-code flow | [Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server) | Server-side confidential client exchanges an authorization `code` for tokens via a POST to the token endpoint | Applies directly — this is the exact flow `connected_accounts.py`'s connector-consent route already implements | None |
| PKCE behaviour | Same source; confirmed by direct code inspection during the Phase 4C integrity check | Not required for confidential web-server clients by Google's own documentation, but present in LifeFlow's implementation for both flows | Applies — `code_challenge`/`code_challenge_method=S256` sent on the connector `/connect` redirect, `code_verifier` sent at exchange | None — Phase 4C's correction (PKCE was always present) stands |

## Fresh-verification conclusion

The current official requirements remain fully compatible with the approved Phase 4D design. No requirement authorises, or is used to justify, any scope beyond the existing four, any write operation, or any deployment/verification claim. Two genuine, previously-undocumented leakage risks were surfaced by this recheck (Gmail profile `emailAddress`, Calendar primary `id`) and are addressed structurally in [live-transport-guard-results.md](live-transport-guard-results.md) and the read-only smoke command's design, not merely by instruction to "not print" them.
