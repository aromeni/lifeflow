## P2 findings (fixed this phase)

- **F-P3-01 — Local dev database/cache bound to all host network interfaces.** `docker-compose.yml`'s `db`/`redis` services used the short `"host:container"` port syntax, binding to `0.0.0.0` by default rather than loopback only — since both services carry well-known, intentionally weak/absent credentials, any other device on the same local network could previously have reached them. **Fixed**: both mappings now use `"127.0.0.1:${PORT}:<container-port>"`. Verified via `docker port` and a full test re-run. See [container-runtime-results.md](container-runtime-results.md).
- **F-P3-02 — `next`/`postcss`/`sharp` carried multiple known CVEs.** `pnpm audit` found 17 vulnerabilities (11 high, 6 moderate) — all traced to `next@16.2.10` being one patch release behind its fix threshold, plus two separately-resolved transitive copies of `postcss`/`sharp`. **Fixed**: `next` bumped to `16.2.12`, `eslint-config-next` matched, `postcss`/`sharp`/`js-yaml` pinned via `pnpm.overrides`. Verified: `pnpm audit` dropped to 2 findings (both `brace-expansion`, below); full `web:typecheck`/`web:lint`/`web:test` (90/90)/`web:build` re-run clean; contract generation byte-identical. See [dependency-security-results.md](dependency-security-results.md).

## P2 findings (recorded, not blocking, with an explicit closure condition)

- **F-P3-03 — `TOKEN_KEY` has no rotation capability.** `AesGcmTokenCipher` holds exactly one active key; application wiring constructs exactly one cipher instance with no dual-key registry. A real rotation today would require a dedicated, currently-unbuilt re-encryption migration. **Named owner**: whoever picks up the future production-hardening work (Stage 12/13). **Closure condition**: build the re-encryption migration (Path A) or complete a disposable-account destructive rotation (Path B), per the "TOKEN_KEY rotation — Phase 4 connection blocker" section of [phase-3-decision.md](phase-3-decision.md), before `TOKEN_KEY` is ever rotated in a real deployment or before any Google test account is connected. **Why this doesn't fail Phase 3 outright**: no current exploitable exposure exists — nothing today requires rotating this key, and the encryption itself (not its rotation capability) is sound and unaffected. **Why it still matters**: it is a direct Phase 4 connection blocker and one of the two open conditions that make the Phase 3 decision CONDITIONAL PASS rather than an unqualified PASS. See [secret-rotation-results.md](secret-rotation-results.md).
- **F-P3-04 — `brace-expansion` (2 paths) carried a known DoS advisory at the time this phase's dependency scan was performed, unfixable locally without breaking ESLint.** Both vulnerable paths are exercised only by dev-tooling (`eslint` processing this repo's own source; `openapi-typescript`/`@redocly/openapi-core` processing this repo's own OpenAPI schema) — neither ever processes attacker-supplied input, and neither runs in the deployed production API/web server. A blanket version override was attempted and reverted after it broke `pnpm web:lint` (`minimatch@3.1.5`, a transitive dependency this project does not control, cannot consume the only patched major line). **Closure condition**: resolved once `eslint`'s own dependency chain bumps its `minimatch` usage upstream. **Recorded as open, not reclassified, in this task**: a same-day revalidation (see the "Revalidation performed for this correction task" section of [dependency-security-results.md](dependency-security-results.md)) found `pnpm audit` now reports zero findings against the unchanged lockfile, and a direct cross-check against GitHub's advisory database confirms all three installed `brace-expansion` versions fall outside every published vulnerable range. This task does not declare F-P3-04 closed on the owner's behalf — it is presented as new evidence for the owner's own review.
- **F-P3-05 — Backups are not retroactively affected by later deletion (documented limitation, not a defect).** Proven directly this phase ([backup-retention-results.md](backup-retention-results.md)): a conventional point-in-time backup taken before a deletion still contains the pre-deletion state after restore — expected behaviour for any backup mechanism, but one that means a real deployment needs an explicit backup-retention/expiry policy aligned to data-retention rules. **Closure condition**: build that policy before production backups exist (Stage 12/13); no production backup infrastructure exists yet for this to misapply to today.

## Automated-suite regressions

None in product code. One genuine test-script defect was found and fixed:

- **T-P3-1 — `test_stage11a_phase3_log_privacy.py` left a rate-limit bucket key in the shared dev Redis (db 0).** The first full-suite run (915 tests collected) showed 7 failures/2 errors, all in tests unrelated to log-privacy's own assertions (`test_stage11a_phase3_owner_scoping.py`, `test_stage11a_phase3_token_sentinel_search.py`, and the pre-existing `test_worker_app.py::test_recover_stale_action_executions_delegates_to_the_sweep`) — every one of them passed in isolation and in smaller batches, the signature of shared-state pollution rather than a real defect, matching the exact root-cause class Phase 2's own defect register already documented (accumulated Redis state from this session's own long sequence of manual `redis-cli` inspections and script runs). Root-caused directly: the log-privacy test's rate-limit-exhaustion stage created a real bucket key with a 3600s TTL via `RateLimiter.check()` and never deleted it, leaving 5 leftover keys (one per parametrized cycle) in the same Redis database other tests share. **Fixed** by deleting the key explicitly in the test's `finally` block. **Verified**: a full clean re-run of the entire backend suite (915 tests) passed 100%, 91% coverage, in a single run with zero failures.

Every pre-existing test suite re-run this phase (199 existing security-relevant tests, fresh) and all 80 new Phase 3 tests passed cleanly in the final verified run, and the full web/API verification gate (below) confirms zero regressions from the dependency bump, the docker-compose change, or this fix.
