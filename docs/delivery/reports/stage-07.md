## Deep architecture and completion review, round 5 (2026-07-19)

A first-principles audit of the entire Stage 7 contract (original promise → implementation → reachable user flow → safety guarantees → automated proof → real sandbox proof), prompted by the observation that Gmail worked end to end on the real sandbox account while Calendar had no demonstrated real-user approval path.

### Findings

1. **Real Calendar execution was unreachable (blocker).** The only composer route into `create_calendar_event` (`_calendar_candidates`) required an already-imported calendar event whose title contains "(proposed)" with a non-empty attendee list — a demo-dataset convention (`ev-007 "Data audit kickoff (proposed)"`) that had silently become the production dependency. No detector recognised scheduling prose ("please schedule"/"please add" are outside the closed request-cue verb list) and no code path extracted event details from email text, so a controlled real scheduling email produced no signal at all. Worse, on a real account the "(proposed)" route would have created a **near-duplicate sibling** of the user's own placeholder event. Sync, OAuth, the executor, and every approval/context binding were verified sound — the gap was purely that the executor had no road to it, failing the stage-plan exit criterion "approves draft/**event**".
2. **Calendar verification was weaker than Gmail's and weaker than documented.** The executor trusted `events.insert`'s own response and compared only `summary` + attendees — never start/end, and never an independent read — while the ADR's verification decision promised start/end/attendees/summary confirmation, and Gmail had already moved to an independent re-fetch (D17/D35).
3. **Solo synced events silently vanished.** `detect_meetings`' two-attendee threshold kept solo events out of "Today and upcoming" with no disclosure anywhere — repeatedly mistaken for a sync failure during live testing.
4. **The demo E2E encoded pre-D36 semantics.** It asserted "exactly 3 proposals after regeneration" and had not been re-run since D36; under walk-past-terminal, regenerating after executing the task proposal legitimately surfaces the next-ranked evidenced task.

### Fix (ADR 0003 D39–D41)

- **D39 — deterministic scheduling-intent path (Model A):** new `scheduling_phrases.py` (closed cue set + strict title/full-date/time/duration/timezone/attendee extraction; nothing guessed; ambiguity and past dates fail closed), new `SignalType.schedule_request` + `detect_schedule_requests` (complete+future ⇒ 0.9; incomplete ⇒ 0.45, a visible low-confidence clarification signal), and `_scheduled_event_candidate` composing an exact `CalendarEventCreatePayload` from the evidence email, with a duplicate guard (`existing_event_duplicate`) against events already on the synced calendar. Everything downstream (origins, D36 walk, approval binding, execution context via evidence `source_account_id`, policy, executor, audit) unchanged.
- **D40 — independent Calendar verification:** `CalendarEventClient.get_event` (read-only; write surface unchanged and still structurally asserted) + executor re-fetch verifying non-cancelled status, exact title, start/end **as instants** (Google-normalised offsets), and attendees (only the calendar owner tolerated as an extra). Re-fetch failure or mismatch after insert ⇒ `uncertain`, never `failed`, never retried; 4xx on the insert itself remains final.
- **D41 — truthfulness:** the "(proposed)" placeholder route now composes from synthetic evidence only (`google_account_ids` threaded from `generate_from_brief`), and the brief gains a calm `calendar_events_not_listed` notice for future timed sub-2-attendee events. The demo E2E was updated to assert D36 semantics precisely (terminals preserved byte-for-byte; exactly one new `proposed` task from a distinct origin).

## Real sandbox-account verification, round 4 (2026-07-18)

Confirming D35/D37 live (round 3) surfaced a fourth defect: `POST /connected-accounts/google/sync` started returning `502 Bad Gateway` on every attempt.

### Root cause

Gmail's `history.list` call succeeded, returning message ids including the underlying message of the Gmail draft created during the round-3 live test. Fetching that specific message via `messages.get` returned `HTTP 404` (per Gmail's own documented behaviour, a history entry can reference a message no longer retrievable — here, the draft's underlying message had been superseded by a later edit). `GoogleEmailConnector._resolve_messages` had zero error handling around that per-message fetch, so the 404 propagated as an unhandled `GoogleClientError` all the way up through the connector, `IngestionService`, `GoogleSyncService.sync`, and the route handler — failing the *entire* sync because of *one* unresolvable message, exactly the kind of all-or-nothing failure this project's own design principles (and the earlier `gmail_excluded`/`calendar_incomplete` split) exist to prevent.

### Fix

`_resolve_messages` now catches `GoogleClientError` around each `get_message` call: a `404` increments a new `incomplete_count` and skips just that message; any other status still re-raises, keeping the carve-out narrow to the one documented, benign case. `gmail_incomplete` (new field, parallel to `gmail_excluded`/`calendar_incomplete`) is threaded through `GoogleSyncSummary` → `GoogleSyncResponse` → contracts → `connections/page.tsx` (a `role="alert"` notice, since — unlike `gmail_excluded` — this is a genuine failure). See ADR 0003 D38.

### Tests

Two connector-level tests (a 404 on one history-referenced message is skipped, counted, and the rest of the batch + the sync still complete normally; a non-404 client error still propagates, proving the carve-out stays narrow), one `GoogleSyncService`-level test, and one full HTTP route-level test proving `POST /connected-accounts/google/sync` now returns `200` with `gmail_incomplete: 1` instead of `502` for the exact scenario observed live.

### Verification

Backend **364 passed** (4 net new), mypy strict and ruff clean. Frontend **38 passed** (1 net new), typecheck/lint/format/build clean. Contracts regenerated (`gmail_incomplete` added to `GoogleSyncResponse`).

**Outstanding**: a live "Sync now" against the real sandbox account, to confirm this fix resolves the actual `502` observed — fixed and tested, but not yet re-run live.

## Real sandbox-account verification, round 3 (2026-07-18)

With round 2's generation fix live, a real sign-in attempt (not the Connect-Google consent flow — plain "Sign in with Google") failed on every try: the button appeared to do nothing beyond a brief flash, landing back on the homepage with `?auth_error=invalid_id_token` in the URL, never reaching `/connections`.

### Root cause

Server logs showed the OAuth token exchange and the JWKS certs fetch both succeeding (`200 OK` from `oauth2.googleapis.com/token` and `www.googleapis.com/oauth2/v1/certs`); only ID-token verification itself failed, and the existing `except IdTokenVerificationError` handler logged just a generic message with no traceback, hiding the real cause. Adding `exc_info=True` and reproducing once more revealed: `google.auth.exceptions.InvalidValue: Token used too early, <now> < <iat>` — a **4-second** gap between the local machine's clock and Google's token-issuance timestamp, confirmed by comparing `date -u` against the `Date` header of a live response from a real Google endpoint (no meaningful skew by any reasonable measure). `google.oauth2.id_token.verify_oauth2_token()` defaults to `clock_skew_in_seconds=0` — zero tolerance — so this entirely ordinary amount of drift hard-failed verification every single time.

### Fix

`google/oauth.py::_default_verifier` now passes `clock_skew_in_seconds=10` to `verify_oauth2_token()` — a conventional tolerance that only widens the issued-at/expiry boundary check, leaving signature/audience/issuer verification untouched. See ADR 0003 D37.

### Tests

None added: `_default_verifier` is exercised only through real `google-auth`/network calls by design (D14), and every existing test already substitutes an injected `verifier` stub, so this change isn't observable from the test suite. Verified live instead: repeating the real sign-in flow after the fix reached `/connections` successfully.

### Confirms D35 end-to-end

With sign-in fixed, the proposal generated by round 2's fix (for the "LifeFlow Gmail verification test 2" email) was approved and executed live against the real sandbox account. Result: `"status": "succeeded"` (not `uncertain`) — `draft_id`, `message_id`, and `thread_id` all present and verified. ## Real sandbox-account verification, round 2 (2026-07-18)

Round 1 left one item open: a second real Gmail sandbox draft, executed against a genuinely fresh proposal, to confirm D35's corrected verification path reports `succeeded` end-to-end. Attempting exactly that surfaced a different, more fundamental defect instead.

### Root cause

A new, real email was sent into the connected sandbox mailbox. It appeared correctly in the next generated brief, but **no `create_gmail_draft` proposal was ever created for it** — not rejected, not filtered, simply never generated. The Approval inbox still showed only the three pre-existing proposals from round 1 (the `uncertain`-execution Gmail draft, a rejected Temu draft, a rejected internal task).

Trace of the full path (brief signal → candidate composition → origin fingerprint → dedup → persistence → `GET /action-proposals`):

- The new message's `SourceItem`/`Signal` were extracted correctly (correct external message id, thread id, `signal_type=request`, action-eligible).
- `compose_proposal_candidates` (`proposal_composition.py`) never composed a candidate from it at all. Each of `_task_candidate`/`_draft_candidate`/`_calendar_candidate` iterated the brief's signals in ranked (priority) order and `return`ed on the **first** eligible match — full stop. The older email's `request` signal outranked the new one (higher priority score) and was returned every time; the new signal was never reached, so it was never turned into a `ProposalCandidate`, regardless of the old proposal's status.
- `ActionProposalService.generate_from_brief`'s origin-fingerprint dedup logic (`get_by_origin`, `created`/`updated`/`unchanged`/`preserved` accounting) was never at fault and required no change in isolation — it simply never received a second candidate to evaluate for `create_gmail_draft`.
- `ActionProposalRepository.get_by_origin`/`.list()` and the `GET /action-proposals` route were confirmed correct throughout: origin fingerprints (`sha256(action-origin-v1 | action_type | signal.dedupe_key)`, and `Signal.dedupe_key = sha256(signal_type | sorted evidence_refs)` under a per-user uniqueness constraint) are already unique per distinct signal, and the list route has no proposal-count limit that could plausibly exclude a third row (`limit=100`, unpaginated).
- No proposal-count cap was ever actually hit; the exclusion happened purely at candidate-composition time, before any dedup or persistence logic ran.

### Fix

Decoupled "how many candidates can exist" from "how many are ever considered": `_task_candidate`/`_draft_candidate`/`_calendar_candidate` were renamed to `_task_candidates`/`_draft_candidates`/`_calendar_candidates` and now collect **every** eligible, independently-validated candidate per type in ranked order, instead of returning the first. `ActionProposalService.generate_from_brief` groups the composed candidates by action type and walks each group in ranked order: a brand-new origin is created and the walk stops (one active proposal per type, the existing product cap, unchanged); an existing proposal in `proposed`/`edited`/`approved` still occupies that slot and the walk stops (identical reuse/update/unchanged behaviour to before); an existing proposal that is `rejected`, `executed`, `failed`, `expired`, or `executing` (a dead-ended `uncertain` outcome, never auto-retried per D16/D35) is left completely untouched — still counted as `preserved` — and the walk **continues** to the next-ranked candidate of the same type. See ADR 0003 D36 for the full design.

### Tests

New file `test_proposal_generation_dedup.py` (9 tests): a distinct new signal produces a fresh proposal despite an existing `uncertain`/`rejected`/`executed`/`failed` proposal for an older signal, each left provably unchanged; two different Gmail threads from the same sender compose to two distinct origin fingerprints; the one-active-proposal cap is filled by a later candidate when two earlier-ranked candidates are both protected/terminal; regenerating the same pair of signals afterwards is idempotent; `GET /action-proposals` actually surfaces the new proposal alongside the untouched uncertain one (a real dev-login/HTTP route test, using a `SourceItem` built through the same `normalisation.email_to_source_item` the real Google connector uses); and the original uncertain execution is confirmed unchanged (same execution id, same outcome) after the new proposal is generated — it was never retried.

### Verification

Backend **360 passed** (9 net new), mypy strict and ruff clean, `ruff format --check` clean. No contract, migration, or frontend change this round (the bug and fix are entirely backend generation logic; the round-1 "Execution outcome uncertain" UI label already covers how the untouched old proposal displays).

### Existing uncertain record preservation

The round-1 `create_gmail_draft` proposal and its `uncertain` `ActionExecution` were never modified, retried, or re-executed at any point during this investigation or fix — confirmed by direct assertion in the new test suite (same execution id, same `uncertain` outcome, proposal status still `executing`, both before and after the new proposal is generated), not merely by inspection.

## Focused remediation, round 3 (2026-07-17)

A focused independent review returned **BLOCK** on one remaining issue in the round-2 remediation: `ActionPolicyEngine.validate_execution` re-verified the approved execution context correctly, but strictly *before* the durability commit (ADR 0003 D16) that intentionally releases every lock the transaction held, since the real Google call that follows may be slow. `GoogleTokenService.get_valid_access_token(provider)` then obtained the real token afterwards through a bare `(user, provider)` lookup that checked only account status — never the approved `authorisation_revision` or scope. Between the commit and the real Gmail/Calendar HTTP call, a concurrent disconnect/reconnect or scope change went undetected, and the actual write could proceed under a different authorisation than the one the user approved — the exact post-commit TOCTOU window the review brief described.

Fixed — see ADR 0003 D34 for the full design:

- **`ApprovedExecutionAuthorization`** (`execution_context.py`, new): an immutable `(connected_account_id, provider, authorisation_revision, required_scope, execution_context_hash)` snapshot built only from `ActionProposal.approved_*` columns, never from a fresh account read. `None` for a simulated approval. Threaded explicitly through `ActionProposalService.execute() -> ExecutorRegistry.execute() -> GoogleGmailDraftExecutor`/`GoogleCalendarEventExecutor -> GoogleTokenService.get_valid_access_token_for_execution` — every layer's `execute()` signature now carries it.
- **`GoogleTokenService.get_valid_access_token_for_execution`** (`accounts.py`, new): selects the account by both `connected_account_id` and `user_id` under `SELECT ... FOR UPDATE`, and — under that same lock, before decrypting or refreshing anything — re-verifies provider, status, `authorisation_revision`, and `required_scope` all still match exactly. Any mismatch raises `ApprovedExecutionContextChangedError` strictly before any Gmail/Calendar HTTP call; a routine refresh (unchanged revision) proceeds exactly as before via a helper now shared with the existing `get_valid_access_token`.
- **`populate_existing()` correctness fix** (`repositories.py`, `accounts.py`): this app's session dependency uses `expire_on_commit=False`. `execute()` already reads the account list once (pre-commit) via `ConnectedAccountRepository.list()`, loading the row into the session's identity map; without `populate_existing()` on every `ConnectedAccountRepository` read and the new exact-account query, SQLAlchemy silently returns that stale in-memory copy even after a concurrent transaction commits a change and even under a genuine `FOR UPDATE` lock. The round-3 race tests caught this directly — a first pass of the fix passed every test except the two using a genuinely independent second PostgreSQL session — and it would otherwise have silently defeated this remediation (and quietly undermined the existing D29 pre-commit check) in production.
- **Error classification**: `ApprovedExecutionContextChangedError` is caught inside the Google executors and re-raised as `FinalExecutionError("approval_context_changed")`, reusing the existing final-failure plumbing. `ActionExecution.outcome` becomes `failed` (never `uncertain`), `error_code = "approval_context_changed"`, with a message stating plainly that no external action was attempted; the proposal moves to the existing terminal `failed` status.
- **Test-only deterministic barrier**: `ActionProposalService` gained an optional `post_commit_hook` (no-op by default) that fires exactly once, synchronously, immediately after the durability commit and before the executor runs; `action_proposals.py`'s execute route reads an equally optional `app.state.action_execution_post_commit_hook` (`None` in every real deployment). This lets the race-test suite interleave a genuinely independent second session at exactly the window the fix closes, without timing-based flakiness.
- **Low-cost review findings**: the Approve button is now disabled/absent whenever `execution_mode === "unavailable"` (previously server-side only); tamper tests were added for a corrupted `approved_authorisation_revision` and `approved_execution_context_hash`.

New tests (18): `test_google_token_execution_race.py` (7 — reconnect/scope-removal races for Gmail and Calendar through the real executor/token-service path, a routine-refresh regression, a pre-commit-layer regression, and one full HTTP route-level race), 9 new `GoogleTokenService.get_valid_access_token_for_execution` unit tests in `test_google_token_service.py` (exact match, unknown/wrong-user/wrong-provider/inactive/revision-mismatch/scope-missing account, routine refresh, `invalid_grant`), 1 defensive `approved_authorization=None` test in `test_google_executors.py`, plus 2 new tamper cases in `test_action_policy_tamper.py`. `test_google_executors.py`'s existing tests were updated for the new required `approved_authorization` parameter.

Focused-remediation gate results: backend **340 passed** (18 net new), coverage regenerated; mypy strict and ruff clean; web 29 tests (2 new)/lint/typecheck/format/build clean; alembic upgrade/check clean (no schema change this round); contracts unchanged (no API schema change); pre-commit, detect-secrets, and gitleaks (full history) clean; `git diff --check` clean.

## Independent review and remediation, round 2 (2026-07-17)

A second independent review — of the D25–D28 wiring/disclosure remediation — again returned **BLOCK**, finding three further correctness and consent-boundary gaps:

1. **Execution context not bound to approval.** `resolve_execution_mode(action_type, accounts)` decided `simulation | real | unavailable` from "does *any* currently active, correctly-scoped account exist", recomputed fresh at both approval and execution time — never from which account the proposal's own evidence actually came from, and never re-checked against what was true when the user approved. This permitted: approving a synthetic-evidenced proposal and having it silently become real once Google was connected; approving against a Google account and having it silently fall back to simulation once that account was disconnected; and a stale approval surviving a reconnect to a different Google account undetected.
2. **OAuth token-endpoint errors under-classified.** `GoogleOAuthClient._parse_token_response` raised one generic `GoogleOAuthError` for every non-200 response other than `invalid_grant` — `429`, `5xx`, `server_error`/`temporarily_unavailable`, and `invalid_client`/`invalid_request` were all indistinguishable and uncaught by the executors' `except GoogleAuthError | GoogleClientError | GoogleTransientError` clauses, so a transient provider failure during a mid-execution token refresh crashed as an unhandled exception instead of the designed `uncertain` outcome.
3. **Pagination cursor data loss.** The Gmail/Calendar connectors already bounded their page loops, but hitting that bound while a `nextPageToken` remained still let the last-fetched page's historyId/syncToken become the committed cursor — permanently skipping every page beyond the bound on the next sync, with no record that anything was missed.

All three are fixed — see ADR 0003 D29–D33 for the design and the sections below for what changed and how it's tested. The two non-blocking findings (the allow-list-assertions clarification, and the route-level/E2E verification asks) are also closed.

### Approval-context binding

`execution_context.py` (new) is the single source of truth for "what would/does executing this proposal actually do" — `resolve_execution_context(action_type, *, accounts, evidence_sources)` binds to the proposal's own evidence (`SourceItem.source_account_id`, resolved from `source_refs`), never to "is anything connected": synthetic/unlinked evidence is permanently `simulation` regardless of what's later connected; Google-sourced evidence is `real` only if the *exact* source account is still active and scoped (never substituted, never a silent fallback); evidence spanning more than one external account is `unavailable` (fail closed). `ActionProposal` gains an immutable approved snapshot (migration `0008`: `approved_execution_mode`, `approved_provider`, `approved_connected_account_id`, `approved_authorisation_revision`, `approved_required_scope`, `approved_source_account_id`, `approved_execution_context_hash`), and `approval_binding_hash` now binds the execution-context hash alongside action type/payload/version. Approval rejects a stale preview (`stale_execution_context`, 409); execution reconstructs the current context and refuses on any difference (`approval_context_changed`), atomically invalidating the stale approval rather than leaving it retryable. `ConnectedAccount.authorisation_revision` (new, bumped only on a genuine OAuth consent grant, never on a silent token refresh) is what makes a reconnect — including to a different Google account, which OAuth alone can't distinguish from the same account re-consenting — invalidate a stale approval. See ADR D29/D30.

### OAuth refresh classification

`GoogleOAuthClient` now classifies every non-200 token-endpoint response through one mapping, reusing the existing typed errors (no new classes): `invalid_grant` → `InvalidGrantError`; `429`/`5xx`/`server_error`/`temporarily_unavailable` → `GoogleTransientError` (→ `uncertain`); `invalid_client`/`unauthorized_client` → `GoogleAuthError`; `invalid_request`/`unsupported_grant_type`/`invalid_scope`/any other definitive 4xx → `GoogleClientError` (→ a controlled final failure). See ADR D31.

### Cursor safety

`google_sync_cursor.GoogleSyncCursor` (`committed_cursor`, `continuation_page_token`, `continuation_base_cursor`, `sync_in_progress`, `last_complete_sync_at`) replaces the bare-string cursor. The committed cursor only ever advances on a true final page; a page-bound-truncated attempt persists a continuation instead, which a later sync resumes from (Gmail: same `startHistoryId`; Calendar: `nextSyncToken` only trusted on the genuine final page; windowed continuations persist their exact `since`/`until`). An expired or rejected continuation safely falls back to a fresh bounded resync. `GoogleSyncResponse` gains `gmail_sync_complete`/`calendar_sync_complete` so an incomplete sync is reported truthfully. See ADR D32.

## Independent review and remediation, round 1 (2026-07-17)

An independent review of the first Stage 7 pass returned **BLOCK**. It found that the OAuth, token, narrow-client, connector, and durable-execution modules (D10–D24) were each individually well-built and unit-tested, but three blockers meant the application did not actually do what the report claimed:

1. **Production wiring gap.** `GoogleSyncService` and the Google executors existed but were never constructed by any route — every execute call defaulted to `SimulatedExecutorRegistry`, and no route ever called `GoogleSyncService.sync()`. A connected Google account changed nothing about what the running app actually did.
2. **Execution disclosure gap.** `ActionProposalResponse.simulation_only` was a static `True` default, never computed from reality, and the frontend hard-coded "Simulation only"/"Simulation result" labels regardless of what would actually happen.
3. **Transport-error gap.** The Gmail/Calendar clients and the OAuth refresh call only classified HTTP responses that arrived; a genuine timeout or connection error propagated as an unclassified exception instead of the designed `uncertain` outcome.

All three are fixed — see ADR 0003 D25–D28 for the design, and the sections below for what changed and how it's tested. The four non-blocking findings (OIDC `nonce`, pagination-bound tests, a Calendar prompt-injection fixture, and a disconnect test that didn't actually simulate an unreachable revoke endpoint) are also closed (D28 and the test-coverage table below).

## Outcome

LifeFlow now connects the proven Stage 3–6 workflow to real Gmail and Google Calendar, disabled by default and gated behind explicit configuration (`GOOGLE_OAUTH_ENABLED=true` plus two separate OAuth client configs). A test user can sign in with Google (app authentication only), separately connect Gmail/Calendar (data-access consent only), trigger a real sync from the Connections screen, generate a brief from that real ingested data, approve a Gmail draft or calendar event that — for a correctly-scoped connected Google account **whose own evidence that draft/event was proposed from** — is actually created via the real Gmail/Calendar API (never send, never delete, never modify an existing event), and see a complete, truthful audit trail. Production wiring exists (round 1); execution context is approval-bound, never recomputed loosely from "is anything connected" (round 2, D29/D30); Gmail/Calendar cursor continuation is loss-safe under a page bound (round 2, D32); OAuth refresh-failure classification is complete across every non-200 response, not just the ones that happened to arrive as a response at all (round 2, D31). The API and UI say plainly, before and after every approval, whether an action is real or simulated, and now also whether the execution context has changed since approval. Demo mode, dev-login, and every Stage 3–6 guarantee remain unaffected when the feature is off, which remains the default.

- **Two independent OAuth flows (ADR 0003 D10):** `GET /auth/google/login` + `/auth/google/callback` (app sign-in, `openid email profile` only, separate OIDC client) and `GET /connected-accounts/google/connect` + `/callback` + `POST /disconnect` (connector consent, the four data scopes only, separate connector client, `access_type=offline&prompt=consent` to guarantee a refresh token).

### New in this remediation (ADR 0003 D25–D28)

- **`POST /connected-accounts/google/sync`** (D25): the route that turns a connected account into real, persisted `SourceItem`s. Owner-scoped; verifies read scopes per source (skips whichever half wasn't granted rather than failing the whole sync or calling an unauthorised endpoint); obtains a token via `GoogleTokenService`; runs the existing `IngestionService`; persists cursors only after success; returns imported/updated/unchanged/incomplete counts and each side's cursor status; records the existing `sync.completed` audit event. Triggered only by the user (a "Sync now" button on the Connections screen) — never automatically.
- **`google_wiring.py`** (D25): the single place both the sync route and the execute route ask "is Google wired for this deployment, and if so, build the request-scoped service" — `build_google_sync_service()` / `build_google_executor_registry()`, both `None` when `GOOGLE_OAUTH_ENABLED` is false.
- **`action_policy.resolve_execution_mode()`** (D26): the one function that decides `simulation | real | unavailable` for a proposal, from the same account snapshot the policy engine validates against — called by both the policy check and `ActionProposalService.execute()`, so they can never disagree. Decided before execution, never chosen reactively after a real call fails; a resolved-`real`-but-unwired request fails in a controlled way (`FinalExecutionError("google_execution_unavailable")`), never silently simulating.
- **`ActionExecution.execution_mode`** (migration `0007`, D26): persisted once at creation, never recomputed, so a historical record stays truthful after account settings change. `ActionProposalResponse.execution_mode` is the live, forward-looking counterpart shown on the approval preview. `simulation_only` is retained on both, always derived from `execution_mode`.
- **Frontend truthfulness** (D26): `ActionProposalPanel.tsx` and `approvals/page.tsx` render exclusively from `execution_mode` — distinct copy for simulation / real-Gmail / real-Calendar / unavailable before approval, and for Gmail-draft-created / Calendar-event-created / simulation-result / uncertain / failed after execution. The Connections screen gained a "Sync now" control and a result summary linking back to Today.
- **Transport-failure classification** (D27): every Gmail/Calendar client call and the OAuth refresh call now catches `httpx.HTTPError` (timeout, connection error — no response ever received) and raises `GoogleTransientError` immediately, matching how a 5xx response was already handled. The Google executors also moved token acquisition inside their error-handling scope, converting `ReauthorisationRequiredError` into a controlled final failure instead of an unhandled exception.
- **OIDC `nonce`** (D28, non-blocking): generated and bound to the sign-in attempt's session state; validated against the ID token's `nonce` claim (which `google-auth` does not check itself); never generated for the connector-consent flow, which has no ID token to bind it to.

### New in round 2 (ADR 0003 D29–D33)

- **`execution_context.py`** (new, D29): `resolve_execution_context(action_type, *, accounts, evidence_sources)` replaces `resolve_execution_mode` as the single source of truth for `simulation | real | unavailable` — bound to the proposal's own evidence provenance, never to "is anything connected".
