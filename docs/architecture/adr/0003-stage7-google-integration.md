# ADR 0003 — Stage 7 Google Integration

**Status:** Accepted · **Date:** 2026-07-17 · **Stage:** 7

## Context

Stage 6 delivered the complete proposal/approval/execution loop against simulated executors only. Stage 7 connects that proven loop to real Gmail and Google Calendar. This ADR records the concrete decisions needed before implementation, refined through a design review that identified several gaps in the initial pass — each is recorded below with the corrected decision, not just the final answer, so the reasoning survives.

## Decisions

### D10 — Two independent OAuth interactions with Google, two separate client configurations

LifeFlow application sign-in (OIDC) and Google connector consent (Gmail/Calendar data scopes) are implemented as genuinely separate OAuth clients, settings, and redirect URIs — not one client reused for two purposes:

```text
GOOGLE_OIDC_CLIENT_ID / GOOGLE_OIDC_CLIENT_SECRET / GOOGLE_OIDC_REDIRECT_URI
GOOGLE_CONNECTOR_CLIENT_ID / GOOGLE_CONNECTOR_CLIENT_SECRET / GOOGLE_CONNECTOR_REDIRECT_URI
```

**Why separate, not shared:** a shared client makes it structurally possible for a future change to one flow (e.g. broadening the sign-in redirect URI) to silently widen the other's attack surface. Separate clients keep the sign-in surface (`openid email profile`, no data access) and the data-consent surface (`gmail.readonly`, `gmail.compose`, `calendar.readonly`, `calendar.events`) independently configurable, independently revocable, and independently auditable in the Google Cloud Console. They may point at the same Google Cloud project.

- **(a) App sign-in** — `POST /auth/google/login` → `GET /auth/google/callback`. Scope `openid email profile` only. Verifies the ID token, upserts `User`, creates a LifeFlow session identical in shape to `dev_login`'s. Never touches `ConnectedAccount`. `dev_login` is **not removed** — it remains the permanent, environment-gated demo-mode path.
- **(b) Connector consent** — `GET /connected-accounts/google/connect` → `GET /connected-accounts/google/callback`. Requires an existing LifeFlow session. Scope: the four data scopes (D11). Triggered only from the Connections screen, never implied by sign-in (ADR D3, AC-J2.1).

Both flows are disabled by default (`GOOGLE_OAUTH_ENABLED=false`); when disabled, no Google route performs a live redirect and demo mode is entirely unaffected (D16).

### D11 — Exact connector scopes (unchanged from the design pass)

`gmail.readonly`, `gmail.compose`, `calendar.readonly`, `calendar.events`. One constant, one place. A test pins the exact `scope=` string built into the authorization URL.

**Correction from the design pass:** `gmail.compose` is not "send-incapable" — it is a broad scope that *permits* `users.messages.send`, `users.drafts.send`, and message/label mutation via the Gmail API; it only lacks full mailbox deletion/IMAP-level access relative to `mail.google.com`. The earlier claim that this scope structurally prevents sending was wrong and is corrected here. Draft-only behaviour is enforced by **defense in depth at four independent layers**, not by the scope string:

1. **Closed action-type enum** — `ActionType` has no `send_email` member and a DB `CHECK` constraint enforces it; no code path can construct a proposal, approval, or execution for sending.
2. **Narrow transport client** — `GmailDraftClient` (D13) exposes exactly one write method, `create_draft()`, which POSTs to exactly one fixed path (`/gmail/v1/users/me/drafts`). It has no method that can reach `/messages/send` or `/drafts/send`, and no generic `request()` escape hatch.
3. **Allow-listed endpoints** — the client's base implementation asserts the constructed request path against a closed allow-list (`{"users/me/drafts"}` for writes) before dispatch; an unexpected path raises rather than sends.
4. **Transport-level tests** — a test suite drives the real client against a mocked transport and asserts the *set of HTTP calls actually made* contains only the allow-listed method/path pairs, for every executor code path exercised (§ Testing below). This replaces the originally proposed static grep as the primary safeguard (grep only proves the word `send` doesn't appear in source; it proves nothing about what the client sends over the wire, and a refactor could silently break it without failing any test).

The same four-layer pattern applies to Calendar: `CalendarEventClient` exposes only `insert_event()` (→ `POST /calendar/v3/.../events`, never `update`/`patch`/`delete`), with the same allow-list assertion and transport-level test.

### D12 — Calendar event creation never notifies guests; the approval preview says so explicitly

`CalendarEventClient.insert_event()` always sends `sendUpdates=none` — this is not a parameter the caller can override; it is hard-coded in the one method that performs the write. No attendee is ever emailed an invitation, and no other party's calendar is modified, by any Stage 7 code path.

The approval preview for a `create_calendar_event` proposal shows an additional **immutable, non-editable** field — `guest_notifications: "off"` — bound into the same canonical payload/hash the rest of the preview is bound to (so it cannot be edited away or silently change between preview and execution). UI copy is required to state plainly that guests are **not** notified and their calendars are **not** updated by this action — never language implying an invitation was sent.

**Why this exists:** the design pass identified that Google's default `events.insert` behaviour (notify all guests) would have been an undisclosed, unapproved side channel functionally resembling a "send" — never shown to the user, never covered by the approval preview, and arguably in tension with the "no Gmail send capability" guard rail even though it isn't Gmail. Forcing `sendUpdates=none` removes the side channel entirely rather than merely disclosing it.

### D13 — Narrow, closed-method Google transport clients (new `google/` package)

A new `apps/api/src/lifeflow_api/google/` package holds all vendor HTTP concerns, mirroring the existing `llm/` package's shape:

- `google/oauth.py` — authorization URL construction, PKCE (`generate_pkce_pair`), authorization-code exchange, refresh, revoke; ID-token verification (D14).
- `google/gmail_client.py` — `GmailDraftClient`: `list_messages`, `get_message`, `list_history` (reads), `create_draft` (the one write). Every method builds one fixed URL; there is no method that accepts an arbitrary path or verb.
- `google/calendar_client.py` — `CalendarEventClient`: `list_events` (read, cursor-aware), `insert_event` (the one write, `sendUpdates=none` hard-coded).

Both clients take an injected `httpx.AsyncClient` so tests substitute `httpx.MockTransport` — no live network call is possible from the test suite, and no new mocking dependency (e.g. `respx`) is needed.

Domain services (`action_proposal_service.py`, `extraction.py`, `brief_composition.py`) never import from `lifeflow_api.google`; only the connector adapters (`connectors/google_email.py`, `connectors/google_calendar.py`) and the two new executors do. This preserves the "never couple business logic to Google APIs" guard rail exactly as it already holds for the synthetic adapters.

### D14 — ID-token verification via a maintained library, never hand-rolled

**Correction from the design pass:** the first draft implied JWT/JWKS handling would be written directly. That is rejected. Stage 7 uses **`google-auth`** (Google's own maintained Python library) — `google.oauth2.id_token.verify_oauth2_token()` — which owns JWKS fetching/caching, signature verification, issuer checks, audience checks, and expiry checks. LifeFlow code calls this function through a thin, injectable wrapper (`google/oauth.py::verify_id_token(token, *, client_id, verifier=...)`) so tests supply a stub verifier and never perform real cryptographic verification or network JWKS fetches. No JWT library is added beyond `google-auth`'s own dependency (`pyjwt` via `google-auth`'s transitive chain is never called directly by LifeFlow code).

### D15 — Safe `google_subject` linking; no automatic account merge by email

`User` gains a nullable, unique `google_subject` column (the ID token's `sub` claim). Rules, in order:

1. **`sub` is the sole identity key for Google sign-in.** A returning user is found by `google_subject`, never by email.
2. **`email_verified` must be `true`** in the ID token, or the sign-in is rejected outright (an unverified email is not a trustworthy identity signal).
3. **No automatic linking to a pre-existing user by matching email.** If no user has this `sub`, Google sign-in attempts to create a **new, distinct** `User` row rather than silently merging into any existing one. Silent email-based merging is an account-takeover vector if any party's email is later reused or attacker-controlled; a human-mediated merge is out of MVP scope.
4. **Correction:** `users.email` carries a global unique constraint (Stage 2) — two distinct `User` rows can never share an email, so "creates a new row" is not unconditionally possible. If the email is already taken by a different user (most plausibly a `dev-login` demo user in an environment where both happen to be enabled), the insert is rejected by the constraint; the sign-in fails with a clear, safe `email_already_registered` error — never a raw 500, never a silent merge, never an overwrite. In ordinary operation this does not arise: `dev_login` is permanently gated to `environment == "development"`, and a production deployment with real Google sign-in has no dev-login rows to collide with.
5. A user created via dev-login has `google_subject = NULL` permanently unless a future stage adds an explicit, user-initiated "link your Google account" flow (not built here).

### D16 — Durable execution attempts: `pending → succeeded | failed | uncertain`, modelled on `ActionExecution`, not `ProposalStatus`

**Correction from the design pass:** the original two amendments both refine, not replace, the design-pass draft.

`ActionExecution` gains an `outcome` column (closed enum + `CHECK`): `pending`, `succeeded`, `failed`, `uncertain`. `ProposalStatus` is **unchanged** — no new enum value, no `CHECK` constraint migration on `action_proposals`. While an execution's outcome is `pending` or `uncertain`, `proposal.status` simply stays `executing` (a status Stage 6 already uses as an in-flight marker). The API computes and exposes `effective_status` on the execution resource: `"succeeded"`, `"failed"`, or `"uncertain"` — the last one derived, not just copied, from `outcome` (see staleness rule below). This keeps the already-reviewed, already-constrained `action_proposals` table untouched and puts all the new complexity in the one table that's actually about attempts.

**Sequence, split across two commits so an attempt cannot vanish:**

1. Row-lock the proposal, validate policy (unchanged from Stage 6).
2. Insert `ActionExecution(outcome="pending", ...)` with the full approved snapshot and idempotency key; set `proposal.status = executing`. **Commit immediately** — a deliberate, documented exception to the one-transaction-per-request pattern (`deps.get_db_session`), justified because this specific write must survive a process crash or network failure during the subsequent external call. If the process dies right here, the next read finds a `pending` row and the staleness rule (below) recovers it.
3. Call the real executor (bounded timeout).
4. Classify and commit again:
   - **succeeded** — a clear 2xx *and* the echoed Google resource's defining fields match the approved payload (§ D17). `outcome="succeeded"`, `proposal.status=executed`.
   - **failed** — a clear, final rejection (400 invalid payload, 403 non-scope permission denial, 404). `outcome="failed"`, `error_code`, `proposal.status=failed`. No auto-retry (extends assumption A20).
   - **uncertain** — timeout, connection error, 5xx, or a 2xx whose echoed resource can't be confirmed to match. `outcome="uncertain"`. `proposal.status` stays `executing`.

**Stale `pending` → `uncertain`:** a `pending` row with no `completed_at` older than `STALE_PENDING_SECONDS` (120s — comfortably above the executor's own bounded HTTP timeout) is not "still running", it is "we lost track of it". This is computed lazily on read (mirroring the existing GET-triggered expiry-sweep precedent from Stage 6) and persisted the same way: the first read that notices a stale `pending` row transitions it to `outcome="uncertain"` and returns the updated value. No background scheduler is introduced in Stage 7 (Redis/queues remain deferred to Stage 8 per ADR D2).

**Never auto-retry.** The existing `execute()` replay guard (return the existing `ActionExecution` without calling the executor again) already covers `uncertain` for free, as long as `uncertain` is treated as "already attempted" everywhere `pending`/`succeeded`/`failed` are. A. human-initiated reconciliation action for `uncertain` rows is explicitly **out of scope for Stage 7** — recorded as new deferred debt (Stage 8/9 candidate, see assumptions log).

**UI:** an `uncertain` execution shows a clear, plain-language warning: *"We couldn't confirm this action completed. It has not been retried automatically."* — never phrased as a failure, never phrased as a success.

### D17 — Verification of the resulting Google resource before declaring success

A 2xx response alone is not proof of success. Before `outcome="succeeded"`, the executor re-parses Google's response body and confirms the fields that matter for user trust: for a Gmail draft, the returned message's `To`/`Subject` headers; for a calendar event, the returned `start`/`end`/`attendees`/`summary`. Any mismatch (never expected from a well-behaved API, but not provably impossible) is treated as `uncertain`, not `succeeded` — the system does not tell the user something happened exactly as approved unless it can see that it did.

### D18 — Refresh-token preservation

**Correction from the design pass:** Google's token endpoint does not return a `refresh_token` on every response — only on the *initial* authorization (with `access_type=offline&prompt=consent`); ordinary refresh-token grants return an access token only. The originally sketched reuse of `ConnectedAccountService.store_tokens()` for the refresh path would have overwritten `encrypted_refresh_token` with `NULL` the moment a refresh response omitted it, silently breaking the account. Fixed: `store_tokens()` (used for the initial connect/reconnect) and the new `refresh_access_token()` path both treat `refresh_token=None` as "unchanged" — the existing encrypted value is left untouched — never as "clear the stored token". A test proves a refresh response without a `refresh_token` field leaves the previously stored encrypted refresh token byte-identical.

### D19 — Refresh concurrency control

`GoogleTokenService.get_valid_access_token()` row-locks the `ConnectedAccount` (`SELECT ... FOR UPDATE`, the same pattern already used for proposal row-locking), checks a safety margin (refresh if fewer than 2 minutes remain before `expires_at`), and refreshes-and-updates inside that lock if needed. Google refresh tokens are long-lived and reusable (not single-use/rotating), so a concurrent refresh is wasteful, not destructive — the lock exists to avoid duplicate calls and racing writes, not to prevent token invalidation.

### D20 — Revoked/expired grants produce a clear re-authorisation state

A refresh call answered with `invalid_grant` sets `AccountStatus.revoked` and raises a typed `ReauthorisationRequiredError`, translated by the API into a clear, actionable response — never a bare 500 (AC-J2.3). Disconnect calls Google's token-revocation endpoint before clearing local tokens (best-effort: a failure to reach Google does not block the local disconnect, since the user's control over their own local data must never depend on an external dependency being reachable).

### D21 — Idempotent, cursor-based, bounded ingestion

Both connectors implement the *existing* `EmailConnector`/`CalendarConnector` protocols unchanged — `IngestionService`/`SourceItemRepository`'s idempotent upsert-by-`(user, source_type, external_id)` and `content_fingerprint` change detection needed no changes at all (ADR D6 paying off exactly as intended).

- **Gmail:** first sync bounded to the 14-day window (BD5); subsequent syncs use `users.history.list` with a stored cursor. Google's history can expire (**HTTP 404** on `history.list` with a stale `startHistoryId`) — the connector catches this specific status and falls back to a full bounded resync (re-running the 14-day windowed `messages.list`), then stores a fresh cursor.
- **Calendar:** first sync bounded by `timeMin`/`timeMax`; subsequent syncs use Calendar's native `syncToken`. An invalidated token surfaces as **HTTP 410** on `events.list` — caught specifically, triggering the same full-bounded-resync-then-fresh-cursor fallback.
- **Cursors** live in a new `ConnectedAccount.sync_cursors: dict[str, str]` JSON column, keyed `"gmail"` / `"calendar"` (the two APIs' cursor types are unrelated and must not share a slot).
- **Quota:** conservative page sizes, a bounded page/time cap per sync run, bounded exponential backoff on 429/5xx (never an unbounded loop) — a partial sync is surfaced as "incomplete", never silently hung.
- **Content minimisation:** Gmail messages are fetched with `format=metadata` and an explicit header allow-list (`From`, `To`, `Subject`, `Date`) plus the API's own bounded `snippet` — never the full raw body. This reduces both retention (T15) and prompt-injection surface (T3): less untrusted content is ever ingested per message.

### D22 — Scope-aware policy, additive to the existing synthetic path

`action_policy.py`'s scope check generalises from "any `synthetic` account with the `demo` scope" to a per-action-type table of acceptable `(provider, scope)` pairs — `create_gmail_draft` accepts `("synthetic", "demo")` **or** `("google", "gmail.compose")`; `create_calendar_event` accepts `("synthetic", "demo")` **or** `("google", "calendar.events")`. `create_task` requires no external capability, unchanged.

**Reason-code stability:** per the naming convention ("reason codes are contracts"), the existing `simulated_scope_missing` code is not renamed. It continues to fire whenever *no* acceptable capability is present (synthetic or Google) — existing Stage 6 tests, which never configure a Google account, keep passing unchanged. A Google-connected user with the exact required scope now satisfies the check through the new path; the code that fires when *only* Google is connected but the wrong scope is granted is also `simulated_scope_missing` (same contract, deliberately not split further — the meaning generalises to "no capable connected account", not just "no simulated one"). This is a conscious choice, documented so it doesn't read as an oversight.

### D23 — Everything disabled unless explicit configuration is present

`GOOGLE_OAUTH_ENABLED: bool = False` (new setting), checked at app-factory time exactly like `LLM_EXTRACTION_ENABLED`: when `false`, no Google route is reachable in a way that performs a live redirect, no `google.*` client is constructed, and `main.py` never imports credentials that don't exist. Demo mode's synthetic connectors, dev-login, and the whole Stage 3–6 pipeline are unaffected regardless of this setting. When `true`, both OAuth client configs (D10) must be fully present or the app refuses to start (fail fast, matching the existing `LLM_EXTRACTION_ENABLED` + `ANTHROPIC_API_KEY` pattern).

### D24 — New dependencies

- `httpx` moves from dev-only to a runtime dependency (async calls to Google's token endpoint, Gmail API, Calendar API).
- `google-auth` is added for ID-token verification only (D14) — not `google-api-python-client` (synchronous, and its request-building style would reintroduce a "generic request" surface exactly where D13 requires a closed one).
- No new OAuth-flow library (`authlib` etc.) — the threat model's need for exact control over state/PKCE/redirect validation (T11) is better served by the small amount of hand-written flow code already covered by D13's transport-level tests, than by adopting a general-purpose OAuth client library's opinions about the flow.

### D25 — Application wiring: real sync and execution are reachable through the running app

An independent review of the first Stage 7 pass found that D13/D16/D21's modules (the narrow Google clients, `GoogleSyncService`, the Google executors) were fully built and unit-tested in isolation but never constructed anywhere the running application could reach: every route that touched `ActionProposalService` defaulted to `SimulatedExecutorRegistry`, and no route ever called `GoogleSyncService.sync()`. A connected Google account changed nothing about what the app actually did.

Fixed by adding:

- **`POST /connected-accounts/google/sync`** (`connected_accounts.py`) — the first route that turns a connected account into real, persisted `SourceItem` rows. User-triggered only (never on page load or a timer); locates the caller's own active Google account; skips whichever half (Gmail/Calendar) wasn't granted read access rather than failing the whole sync or calling an unauthorised endpoint (`GoogleReadScopeMissingError` only when *neither* half is granted); persists cursors only after `IngestionService.import_sources` fully succeeds; returns imported/updated/unchanged/incomplete counts plus each side's cursor status (`initial`/`incremental`/`resynced`/`not_granted`).
- **`google_wiring.py`** — the single place that asks "is Google configured for this deployment, and if so, build the request-scoped service": `build_google_sync_service()` and `build_google_executor_registry()`, both returning `None` when `GOOGLE_OAUTH_ENABLED` is false, so both the sync route and the execute route ask the same question the same way and can never drift.
- **`action_proposals.py`'s execute route** now builds a `google_executors` registry via `google_wiring.py` and passes it into `ActionProposalService`, which resolves `real` vs `simulation` per proposal (D26) instead of always defaulting to simulation.

### D26 — Truthful execution-mode disclosure, decided before execution and persisted at creation

`action_policy.resolve_execution_mode(action_type, accounts) -> ExecutionMode` (`simulation | real | unavailable`) is the single function both the policy engine's scope check and `ActionProposalService.execute()` call — the decision of which path a proposal uses is made once, from the same account snapshot policy just validated against, **before** any executor runs, never chosen reactively after a real call fails. If `resolve_execution_mode` says `real` but no `google_executors` registry was wired for this request (a deployment/wiring bug, not a user error — a genuinely unconnected/unscoped account is already denied by policy before this point), `UnavailableGoogleExecutorRegistry` raises a controlled `FinalExecutionError("google_execution_unavailable")` rather than silently falling back to simulation.

`ActionExecution.execution_mode` (`'simulation' | 'real'`, migration `0007`) is set once at creation and never recomputed — a historical execution record stays truthful even if the user's connected accounts change afterwards. `ActionProposalResponse.execution_mode` is the forward-looking, live-recomputed counterpart (what executing *right now* would do), shown on the approval preview; `ActionExecutionResponse.execution_mode` is the persisted historical fact. `simulation_only` is retained on both for API compatibility, always derived (`execution_mode != "real"`), never set independently.

The frontend (`ActionProposalPanel.tsx`, `approvals/page.tsx`) renders exclusively from `execution_mode` — the previous unconditional "Simulation only" / "Simulation result" labels (accurate only because D1 meant *everything* was simulated in practice) are removed. Before approval: simulation / real-Gmail / real-Calendar / unavailable each get distinct, specific copy. After execution: "Gmail draft created" / "Calendar event created" / "Simulation result" / "Outcome uncertain — not retried automatically" / a failure label, chosen from `execution_mode` and `effective_status` together, never from a static string.

### D27 — Raw transport failures are classified `uncertain` immediately, not left as an unclassified crash

The narrow Gmail/Calendar clients and `GoogleOAuthClient.refresh_access_token` previously handled only HTTP responses that arrived (`_raise_for_error` inspects a status code) — a genuine transport failure (`httpx.TimeoutException`, `httpx.ConnectError`, no response ever received) propagated as an unclassified exception, past every `except GoogleAuthError | GoogleClientError | GoogleTransientError` clause in the executors, past `ActionProposalService.execute()`'s `except FinalExecutionError`, to the app-wide generic-500 handler. No data was lost (the `pending` row was already durably committed before the call, per D16), but the user saw a generic `internal_error` instead of the designed `uncertain` outcome, and had to wait for the 120s staleness sweep to see the honest state.

Fixed: every `self._http.get/post` call in `gmail_client.py`, `calendar_client.py`, and `GoogleOAuthClient._post` now goes through a wrapper that catches `httpx.HTTPError` and raises `GoogleTransientError` immediately. The Google executors also moved `GoogleTokenService.get_valid_access_token()` inside their `try` block, catching `ReauthorisationRequiredError` (→ a controlled `FinalExecutionError`, not a crash) alongside the existing Google error types. A repeated `execute()` call after an `uncertain` outcome still returns the existing execution without invoking the executor again (unchanged from D16); no raw exception text, URL, token, or payload ever reaches the API response.

### D28 — OIDC `nonce` (independent-review non-blocking hardening)

`google-auth`'s `verify_oauth2_token()` validates signature, issuer, audience, and expiry, but does not check a `nonce` claim. `state` + PKCE protect the authorization-code exchange but not the ID token's own claims against replay outside the original sign-in attempt. Fixed: `begin_oauth_flow(..., include_nonce=True)` generates and stores a `nonce` alongside `state`/PKCE (OIDC sign-in only — the connector-consent flow never exchanges an ID token, so it never carries one); `build_authorization_url(..., nonce=...)` includes it in the Google redirect; `verify_id_token(..., expected_nonce=...)` rejects a mismatched or missing nonce when one was expected.

### D29 — Approval-bound execution context, not "any capable connected account"

A second independent review of the D25–D28 remediation returned **BLOCK** again. `resolve_execution_mode(action_type, accounts)` decided `simulation | real | unavailable` from whether *any* currently active, correctly-scoped account existed — never from which account the proposal's own evidence actually came from, and never re-checked at execution time against what was true at approval time. This permitted three undisclosed-execution paths: approve a synthetic-evidenced proposal, then connect Google, and execution would silently become `real`; approve against a Google account, then disconnect it while a synthetic account remained, and execution would silently fall back to `simulation`; approve against Google account revision A, reconnect (Google's OAuth alone cannot distinguish "the same account re-consenting" from "a different account connecting" — see D30), and the stale approval would still execute against whatever was now connected.

Fixed with a new `execution_context.py` module and an immutable per-proposal snapshot:

- **`ExecutionContext`** (`mode`, `provider`, `connected_account_id`, `account_authorisation_revision`, `required_scope`, `source_mode`, `source_account_id`) is resolved by `resolve_execution_context(action_type, *, accounts, evidence_sources)` — bound to the proposal's own evidence (`SourceItem.source_account_id`, resolved from `source_refs`), never merely "is anything connected":
  - **Synthetic/unlinked evidence** → `mode` is permanently `simulation`. Connecting Google afterwards never upgrades it — the resolver never even inspects Google accounts on this path.
  - **Google-sourced evidence** → `mode` is `real` only if the *exact* source `ConnectedAccount` is still active and holds the required scope; a different Google account is never substituted (there is structurally only one `google`-provider row per user — D30 — so "different account" reads as a revision mismatch, not a different row). If the source account is unavailable, `mode` is `unavailable`, never a silent `simulation` fallback.
  - **Evidence spanning more than one distinct external account** → `mode` is `unavailable` (fail closed, never guessed).
  - `create_task` is a closed exception: always local/simulated regardless of evidence source, matching its existing behaviour — there is no Google call to bind for this action type.
- **`ActionProposal`** gains an immutable approved snapshot (migration `0008`): `approved_execution_mode`, `approved_provider`, `approved_connected_account_id`, `approved_authorisation_revision`, `approved_required_scope`, `approved_source_account_id`, `approved_execution_context_hash`. `approval_binding_hash` now binds `action_type + canonical_payload + proposal_version + execution_context_hash` (previously missing the context entirely).
- **Approval** (`ActionPolicyEngine.validate_approval`) takes a new `displayed_execution_context_hash` (from `ProposalApprovalRequest`) and rejects a stale preview with a controlled `stale_execution_context` 409 before persisting the snapshot — the same "bind to what the user actually saw" discipline Stage 6 already applies to payload/version.
- **Execution** (`ActionPolicyEngine.validate_execution`) reconstructs the *current* `ExecutionContext` from live account/evidence state and compares its hash against the persisted `approved_execution_context_hash`. Any difference — disconnect, reconnect, scope change, a different source account — raises `approval_context_changed`; `ActionProposalService.execute()` atomically clears the stale approval (`status` reverts to `edited`, same "requires fresh review" state a payload edit already produces) rather than merely denying the one attempt, so a replay can't retry the same stale snapshot.
- The API exposes `execution_context`/`execution_context_hash` (live preview) and `approved_execution_context`/`execution_context_changed` (the approved snapshot vs. current reality) on every proposal response — deliberately omitting `connected_account_id`/`source_account_id`/the revision counter (raw internal identifiers). The frontend shows an amber "Execution context changed since approval" notice and disables Execute whenever `execution_context_changed` is true.

### D30 — Authorisation revision: the signal a same-`ConnectedAccount`-row reconnect needs

`ConnectedAccount` is unique on `(user_id, provider)` (Stage 2) — reconnecting Google, including with a *different* Google account, updates the same row rather than creating a new one, and the connector-consent flow requests no `openid`/identity scope to distinguish which Google account granted consent. A new `authorisation_revision` integer column (default `1`) is incremented unconditionally inside `ConnectedAccountService.store_tokens()` — the method reached only from the OAuth callback route, i.e. only on a genuine consent grant (new connect, reconnect, or a materially different scope grant), never from `GoogleTokenService.get_valid_access_token()`'s silent refresh path. This is what lets an approval remain valid across routine token refreshes while going stale the moment the underlying authorisation actually changes, without the application needing to know whether a reconnect was "the same" Google account or a different one — it treats every reconnect as a new authorisation, which is the safe assumption either way.

### D31 — OAuth token-endpoint error classification, matching the transport-level classification D27 already applies

`GoogleOAuthClient._parse_token_response` raised a single generic `GoogleOAuthError` for every non-200 response other than `invalid_grant` — `429`, `5xx`, `server_error`, `temporarily_unavailable`, `invalid_client`, `invalid_request`, and any other 4xx were all indistinguishable from each other and uncaught by `GoogleTokenService`/the Google executors' `except GoogleAuthError | GoogleClientError | GoogleTransientError` clauses, so any of them crashed as an unhandled exception during a token refresh mid-execution — the exact gap D27 had already closed for the Gmail/Calendar clients' own responses, left open for the token endpoint's non-`invalid_grant` responses.

Fixed with one classifier (`_classify_token_error`) reused by both `exchange_code` and `refresh_access_token`, mapping every non-200 response to an existing, already-handled type — no new error classes:

- `invalid_grant` → `InvalidGrantError` (unchanged: `GoogleTokenService` marks the account revoked and raises `ReauthorisationRequiredError`).
- HTTP `429`/`5xx`, or OAuth error codes `server_error`/`temporarily_unavailable` → `GoogleTransientError` (→ the executors' existing `uncertain` handling — never a generic 500, never treated as final merely because the response was non-200).
- OAuth error codes `invalid_client`/`unauthorized_client` → `GoogleAuthError` (→ the executors' existing `FinalExecutionError("google_auth_rejected")`).
- `invalid_request`/`unsupported_grant_type`/`invalid_scope`, and any other definitive 4xx → `GoogleClientError` with the status code (→ `FinalExecutionError(f"google_client_error_{status}")`).

No Google error description, the token endpoint URL, or client credentials are ever included in the raised exception's message (threat model T6) — only the HTTP status code, already public information.

### D32 — Cursor safety: committed cursor and mid-pagination continuation are no longer the same field

Both connectors' pagination loops (`_MAX_HISTORY_PAGES`/`_MAX_WINDOW_PAGES`/`_MAX_PAGES`) already existed as bounds, but hitting one while a `nextPageToken` remained still let the loop's final iteration's historyId/syncToken become the committed cursor — silently and permanently skipping every page beyond the bound. Fixed with `google_sync_cursor.GoogleSyncCursor` (`committed_cursor`, `continuation_page_token`, `continuation_base_cursor`, `sync_in_progress`, `last_complete_sync_at`), replacing the bare-string cursor `ConnectedAccount.sync_cursors` previously stored:

- The committed cursor only ever advances when a fetch attempt reaches its **true final page** (`nextPageToken` genuinely absent) — never when the configured page bound is reached first. An incomplete attempt persists `continuation_page_token`/`continuation_base_cursor` instead and leaves `committed_cursor` exactly as it was.
- A later sync resumes from a persisted continuation (same `startHistoryId`/`syncToken` base, continuing `pageToken`) rather than restarting from `committed_cursor` (which would re-import already-seen pages) or skipping ahead. A windowed (first-sync/post-resync) continuation persists the exact `since`/`until` it was issued against, so a resumed page request isn't evaluated against a freshly-shifted rolling window.
- **Calendar-specific:** `nextSyncToken` is only ever treated as authoritative on the true final page — a page still carrying `nextPageToken` never causes a new committed sync token to be stored, even if the (real-world-inaccurate) mock/response also includes a `nextSyncToken` on that page.
- An expired historyId/syncToken discovered while resuming a continuation, or a continuation page token Google no longer accepts, safely falls back to a fresh bounded resync rather than raising past the connector or skipping data.
- `GoogleSyncService`/`GoogleSyncResponse` gain `gmail_sync_complete`/`calendar_sync_complete` booleans alongside the existing cursor-status strings, so the Connections screen can report an incomplete sync truthfully instead of as an ordinary success — no page token or provider error detail is included in the response or audit metadata.

### D33 — Non-blocking clarification: the allow-list assertions are not the primary transport safety boundary

The literal-string allow-list assertions inside `GmailDraftClient`/`CalendarEventClient` (D13) read as if they were themselves what prevents a send/delete/update call — they are not; they are a cheap self-check that happens to run before every dispatch. The actual controls, layered, are: a closed public method surface (no method exists that could construct such a call); no generic `request()` passthrough; exactly one fixed transport path per write; scope-aware policy (D22) plus the approval-bound execution context (D29) gating which proposals can reach an executor at all; and the transport-level tests that assert the *set of HTTP calls actually made* rather than trusting source text. Documented here so the assertions are never cited, on their own, as proof of the guarantee.

### D34 — Token-acquisition-atomic authorisation binding (focused remediation: post-commit TOCTOU)

A focused independent review of D29/D30 found that `ActionPolicyEngine.validate_execution` re-verified the approved execution context correctly, but strictly *before* the durability commit (D16) that intentionally releases every lock the transaction held. The real Google token was then obtained afterwards through `GoogleTokenService.get_valid_access_token(provider)` — a bare `(user, provider)` lookup that checked only `status == active`, never the approved `authorisation_revision` or `required_scope`. Between the commit and the real Gmail/Calendar HTTP call — a window D16 deliberately opens, since the external call may be slow — a concurrent disconnect/reconnect or scope change could go undetected, and the actual write would proceed under a different authorisation than the one the user approved.

Fixed by moving the final check to be atomic with token acquisition, not merely prior to it:

- **`ApprovedExecutionAuthorization`** (`execution_context.py`, new): a frozen `(connected_account_id, provider, authorisation_revision, required_scope, execution_context_hash)` snapshot, built *only* from `ActionProposal.approved_*` columns via `approved_execution_authorization(proposal)` — never reconstructed from a fresh account read. `None` for a simulated approval; synthetic executors and `create_task` never receive one.
- **Threaded explicitly** through `ActionProposalService.execute() -> ExecutorRegistry.execute() -> GoogleGmailDraftExecutor`/`GoogleCalendarEventExecutor -> GoogleTokenService.get_valid_access_token_for_execution()` — every layer's `execute()` signature gained an `approved_authorization` parameter (`ActionExecutor`/`ExecutorRegistry` protocols in `action_executors.py`).
- **`GoogleTokenService.get_valid_access_token_for_execution`** (`accounts.py`, new) selects the account by *both* `connected_account_id` and `user_id` under `SELECT ... FOR UPDATE`, then verifies — under that same lock, before decrypting or refreshing anything — that provider, status, `authorisation_revision`, and `required_scope` all still match exactly. Any mismatch raises `ApprovedExecutionContextChangedError` before any token is touched and before any Gmail/Calendar HTTP call. A routine refresh (unchanged revision) proceeds exactly as before, reusing the shared `_decrypt_or_refresh` helper both token-acquisition paths now call.
- **Correctness fix required to make the above real, not cosmetic**: this app's session dependency uses `expire_on_commit=False` (Stage 2). `execute()` already reads the account list once via `ConnectedAccountRepository.list()` before the durability commit, loading the row into the session's identity map; without `.execution_options(populate_existing=True)` on every read in `ConnectedAccountRepository` (`get`, `get_by_provider`, `list`) and on the new exact-account query, SQLAlchemy would silently hand back that *stale* in-memory copy even after a concurrent transaction committed a change and even under a real `FOR UPDATE` lock — the lock would be genuine at the database level while the Python-visible attribute values remained wrong. This was caught by the round-2-required race tests themselves (a naive first pass of this fix passed everything except the two tests that used a genuinely independent second PostgreSQL session, exactly the scenario the review asked for) and would otherwise have silently defeated this entire remediation, and quietly undermined the D29 pre-commit check too, in production.
- **New error classification**: `ApprovedExecutionContextChangedError` is caught inside the Google executors and re-raised as `FinalExecutionError("approval_context_changed")` — reusing the existing final-failure plumbing (D16) rather than adding a new proposal state. `ActionExecution.outcome` becomes `failed` (never `uncertain` — LifeFlow knows it refused to act, it did not fail to observe an outcome), `error_code = "approval_context_changed"`, with a message stating plainly that no external action was attempted. The proposal moves to the existing terminal `failed` status; the one-execution-per-proposal rule already in place means this is not retried, and the UI (`ActionProposalPanel.tsx`) surfaces a dedicated notice distinguishing this from an ordinary execution failure and instructing the user to check for a fresh proposal rather than retry this one.
- **Test-only deterministic barrier**: `ActionProposalService` gained an optional `post_commit_hook` constructor argument (`None`/no-op in every real deployment; `action_proposals.py`'s execute route reads an equally optional `app.state.action_execution_post_commit_hook`, defaulting to `None` via `getattr`) that fires exactly once, synchronously, immediately after the durability commit and before the executor runs — letting the race-test suite interleave a genuinely independent second PostgreSQL session at exactly the window this fix closes, without timing-based flakiness.
- **Non-blocking, low-cost review findings also closed**: the Approve button is now disabled/absent whenever `execution_mode === "unavailable"` (previously enforced only server-side); tamper tests were added covering a corrupted `approved_authorisation_revision` and `approved_execution_context_hash` directly.

### D35 — Independently-verified Gmail draft content (real sandbox-account finding)

The first real Google sandbox test (2026-07-18) approved and executed a `create_gmail_draft` proposal. The draft was confirmed to genuinely exist in the connected Gmail account, but LifeFlow reported the execution as `uncertain`, not `succeeded` — a false negative in verification, not a failure of the write itself. Root cause: `GmailDraftClient.create_draft`'s own response (`drafts.create`) frequently does not include a fully parsed `message.payload`, so D17's original echo-check (comparing `create_draft`'s own response headers against the approved payload) was comparing against fields that were often simply absent, never a genuine mismatch of real content. No duplicate draft was created on replay — the existing durable-execution/idempotency guarantees (D16) held throughout; only the verification step itself was wrong.

Fixed by making verification independently authoritative rather than trusting the write's own response:

- **`GmailDraftClient.get_draft`** (new): a dedicated `GET /gmail/v1/users/me/drafts/{id}?format=raw` call, added to the read allow-list (`drafts/{id}`) — re-fetches the created draft's actual stored content immediately after `create_draft` returns, rather than trusting that response's (often minimal) body.
- **MIME parsing via the standard library, not hand-rolled**: the base64url `raw` RFC822 message is decoded through `email.message_from_bytes(..., policy=email.policy.default)`. This gives case-insensitive header lookup, transparent RFC 2047 encoded-word decoding for Unicode subjects, and consistent CRLF/LF handling for free; `email.utils.getaddresses` normalises recipient formatting (display names, whitespace, comma-separated lists) down to bare addresses for comparison.
- **`GoogleGmailDraftExecutor.execute()`** now calls `create_draft` then `get_draft`, comparing the *independently re-fetched* content's recipients/subject/body against the approved payload — never `create_draft`'s own response. Any failure to complete this second call (timeout, a momentary not-found, any `GoogleApiError`) is classified `uncertain`, never `failed`: by this point the real write has already happened, so an inability to confirm it is honestly "we don't know", not "it didn't work".
- **Thread ID handled per Gmail's actual semantics, not the request**: Gmail only honours a requested reply `threadId` when the message's Subject/References make it a valid continuation of that thread; otherwise it silently starts a new thread. The verified, *actual* `threadId` is recorded in the result for audit purposes, but is never compared against what was requested, and never gates `succeeded`/`uncertain`.
- **UI**: the proposal's dominant status badge previously showed the internal `"executing"` state verbatim for the entire duration outcome is `uncertain`, reading as "still running" rather than "we don't know". `ActionProposalPanel.tsx` now shows "Execution outcome uncertain" as the dominant label in that state.

Tests: `test_google_gmail_client.py` gained `get_draft` coverage including a redacted-realistic response reproducing the exact false-negative shape (RFC 2047 Unicode subject, quoted-printable transfer encoding, CRLF body); `test_google_executors.py`'s Gmail tests were rewritten around the real two-call flow (success, mismatch, verification timeout, unconfirmable re-fetch, declined thread continuation); the real-account route/race integration tests were updated to serve both calls.

### D36 — Proposal generation walks ranked candidates past terminal proposals instead of stopping at the first (real sandbox finding)

A second real Google sandbox test (2026-07-18) sent a genuinely new email while the first `create_gmail_draft` proposal (D35's uncertain-execution finding) still sat untouched, as required. The new email appeared correctly in the latest brief, but no corresponding proposal ever appeared in the Approval inbox — not rejected, not filtered, simply never generated.

Root cause: `compose_proposal_candidates` (`proposal_composition.py`) composed **at most one** candidate per action type per generation pass — each of `_task_candidate`/`_draft_candidate`/`_calendar_candidate` iterated the user's signals in ranked order and `return`ed on the *first* eligible match, regardless of whether that signal already had an associated proposal, and regardless of that proposal's status. Because the older, higher-priority email's `request` signal always ranked first, it was the only candidate ever composed for `create_gmail_draft`; the new email's signal was never even considered, let alone turned into a proposal. `generate_from_brief`'s existing change-aware dedup logic (origin-fingerprint lookup, `preserved`/`unchanged`/`updated`/`created` accounting) was already correct — it simply never received a second candidate to evaluate. This was a generation-time exclusion, not a policy or list-endpoint bug: `GET /action-proposals` (`list_action_proposals`, unpaginated below 100 rows) and `ActionProposalRepository.get_by_origin` (fingerprint = `sha256(action_type | signal.dedupe_key)`, always unique per distinct signal) both behaved correctly throughout.

Fixed by separating "how many candidates can exist" from "how many are ever considered":

- **`_task_candidates`/`_draft_candidates`/`_calendar_candidates`** (renamed, plural): each now collects *every* eligible, independently-validated candidate in ranked order instead of returning the first. `compose_proposal_candidates` returns all of them, grouped implicitly by the order in which each per-type list is concatenated; more than one candidate of the same action type can now be returned from a single pass.
- **`ActionProposalService.generate_from_brief`** groups the composed candidates by `action_type` and walks each group in ranked order. For each candidate: a fresh origin (no existing proposal) is created and the walk stops there — one *active* proposal per action type per pass, exactly the existing product policy. An existing proposal in `{proposed, edited, approved}` (`_ACTIVE_PROPOSAL_STATUSES`) still occupies that one slot — reused/updated/left-unchanged exactly as before, and the walk stops. An existing proposal in any other state — `rejected`, `executed`, `failed`, `expired`, or `executing` (a dead-ended `uncertain` execution outcome, never auto-retried per D16/D35) — is left completely untouched (still counted as `preserved`, for accounting continuity) and the walk **continues** to the next-ranked candidate of the same type, so a distinct, later signal is no longer permanently shadowed by an earlier one's terminal outcome.
- **Origin identity was already sufficient and required no change**: `origin_fingerprint = sha256(action-origin-v1 | action_type | signal.dedupe_key)`, and `Signal.dedupe_key` is `sha256(signal_type | sorted evidence_refs)` under a per-user uniqueness constraint — two different Gmail messages (different `evidence_refs`, hence different `dedupe_key`) always produce two different fingerprints, and this was true before this fix too. The bug was purely that the second fingerprint was never reached.

Tests (`test_proposal_generation_dedup.py`, new): a distinct new signal produces a fresh proposal despite an existing `uncertain`-execution, `rejected`, `executed`, or `failed` proposal for an older signal (each left provably unchanged); two different Gmail threads from the same sender compose to two distinct origin fingerprints; the one-active-slot cap is filled by a later candidate when two earlier-ranked candidates are both protected/terminal; regenerating the same pair of signals afterwards is idempotent (no duplicates, correct `unchanged`/`preserved` counts); `GET /action-proposals` actually surfaces the new proposal alongside the untouched uncertain one, exercised through a real dev-login/HTTP route test using a `SourceItem` built through the same `normalisation.email_to_source_item` the real Google connector uses; and the original uncertain execution is confirmed byte-for-byte unchanged (same execution id, same outcome) after the new proposal is generated.

Once fixed, the newly-generated proposal was approved and executed live against the real sandbox account (2026-07-18) and reported `succeeded` — the D35 verification path finally exercised end-to-end (see the "Real sandbox-account verification, round 2" update in `docs/delivery/reports/stage-07.md`).

### D37 — ID-token verification tolerates a small clock skew (real sign-in flow finding)

A real sign-in attempt against the deployed OIDC flow (2026-07-18) failed every time: the user clicked "Sign in with Google", the button "flashed" (a full round trip to Google and back), and landed back on the homepage with `?auth_error=invalid_id_token`, never reaching `/connections`. Token exchange and the JWKS certs fetch both succeeded (confirmed via server logs); only ID-token verification itself failed, silently — the existing `except IdTokenVerificationError` handler logged only a generic message with no `exc_info`, discarding the real cause.

Root cause, found after adding `exc_info=True` to that log line and reproducing once more: `google.auth.exceptions.InvalidValue: Token used too early, <now> < <iat>` — a **4-second** gap between this machine's clock and Google's token-issuance timestamp (confirmed via `curl`'s `Date` response header from a live Google endpoint: no meaningful clock skew by any reasonable standard). `google.oauth2.id_token.verify_oauth2_token()` defaults to `clock_skew_in_seconds=0` — zero tolerance — so even this trivial, entirely normal amount of drift (unavoidable on any real machine, NTP-synced or not) hard-fails verification every single time sign-in is attempted from this environment.

Fixed by passing an explicit `clock_skew_in_seconds=10` to `verify_oauth2_token()` in `google/oauth.py::_default_verifier` — a conventional tolerance value that only widens the issued-at/expiry boundary check by ±10 seconds; signature, audience, and issuer verification are entirely unaffected. The separate connector-consent flow (`connected-accounts/google/connect`) never requests `openid` and never verifies an ID token, so it was never exposed to this. The temporary `exc_info=True` added during diagnosis was kept permanently (it now matches the sibling `except Exception` branch a few lines below, and logs no sensitive content — no token, no secret, just the exception class/stack and the numeric timestamps involved).

No new test was added: `_default_verifier` is exercised only through real `google-auth`/network calls by design (D14) and every existing test already substitutes an injected `verifier` stub, so the change is not observable from the test suite — it was verified live, by repeating the real sign-in flow after the fix and confirming it reached `/connections`.

### D38 — A single unfetchable Gmail message must not fail the whole sync (real sandbox finding)

Confirming D35/D37 live surfaced a fourth defect: `POST /connected-accounts/google/sync` started returning `502 Bad Gateway` on every attempt. Server logs showed Gmail's `history.list` call succeeding, then the connector calling `messages.get` for each returned message id — one of them (the underlying message of the very Gmail draft created during the D35/D36 live test) returned `HTTP 404`, and that 404 propagated as an unhandled `GoogleClientError` straight up through `_resolve_messages -> _fetch_history -> fetch_recent -> IngestionService.import_sources -> GoogleSyncService.sync -> the route handler`, failing the *entire* sync rather than just the one unresolvable message.

Root cause: `GoogleEmailConnector._resolve_messages` had no error handling at all around the per-message `get_message` call. Gmail's own History API documentation states that a `messageAdded` entry can reference a message that is no longer retrievable (deleted, or — as here — a draft whose underlying message was superseded when the draft was later edited); a robust sync must treat this as an expected, benign outcome for that one message, not a fatal error for the whole batch. This directly violated the project's own stated design principle that a failed connector must not erase prior data and partial failures must stay visible, not fatal — the very reason `gmail_excluded`/`calendar_incomplete` exist.

Fixed by giving Gmail its own genuine-failure counter, parallel to Calendar's `incomplete_count`:

- **`GoogleEmailConnector._resolve_messages`** now catches `GoogleClientError` around each `get_message` call; a `404` specifically increments a new `incomplete_count` and skips just that message, letting the rest of the batch resolve normally. Any *other* status (400, 403, etc.) still re-raises unchanged — the carve-out is deliberately narrow, covering only the documented "stale history reference" case, not masking a genuine, actionable failure such as a mid-sync permission or scope problem.
- **`gmail_incomplete`** (new field, parallel to the existing `gmail_excluded`/`calendar_incomplete` split from the earlier sandbox round) threaded through `GoogleSyncSummary` → `GoogleSyncResponse` → contracts → `connections/page.tsx`, which shows it as a `role="alert"` notice (a genuine failure worth the user's attention, unlike the calm `gmail_excluded` aside).

Tests: a connector-level test proves a 404 on one history-referenced message is skipped (counted in `incomplete_count`) while every other message in the same batch still resolves and the sync still completes normally (never raises); a second connector-level test proves a *non*-404 client error still propagates, keeping the carve-out narrow; a `GoogleSyncService`-level test proves the same behaviour end-to-end with `gmail_incomplete` correctly separated from `gmail_excluded`; and a full HTTP route-level test proves `POST /connected-accounts/google/sync` now returns `200` with `gmail_incomplete: 1` instead of `502` for exactly the scenario observed live.

### D39 — Deterministic scheduling-intent detection: the real-user path to a Calendar proposal (deep-review finding)

The 2026-07-19 deep architecture review established that `create_calendar_event` had **no coherent real-user path**: the only composer route into it required an already-imported calendar event whose title contains "(proposed)" with a non-empty attendee list (`_calendar_candidates`) — a demo-dataset convention (`ev-007 "Data audit kickoff (proposed)"`) that had silently become the production dependency. A real user's inbound scheduling email ("Please schedule a 30-minute calendar event called … for Sunday 19 July 2026, from 4:00 PM to 4:30 PM Europe/London") produced no signal at all: "please schedule"/"please add" are outside `_STRONG_REQUEST_CUES`' closed verb list, and `parse_due_phrase` only understands by/before phrases. Calendar sync, OAuth, the executor, and every safety binding worked; the *proposal generation* layer simply had no route from real evidence to the executor. This failed the Stage 7 exit criterion ("Test user connects Google, gets brief, approves draft/**event**, sees audit").

Decision — **Model A**: inbound Gmail scheduling request → `schedule_request` signal → `create_calendar_event` proposal, implemented deterministically end to end:

- **`scheduling_phrases.py`** (new, mirrors `deadline_phrases.py`): a closed cue set (`please schedule/arrange/book`, `can/could/would you schedule/arrange/book`, `please create/set up a (calendar) event/meeting/call/appointment`, `add this/it/that to my calendar`, `shall/can/could we meet`, `are you available on`, `set up a meeting`) plus strict field extraction — quoted-or-subject title, **full date only** (a year-less date or bare weekday is never resolved; a stated weekday that contradicts the date, or two conflicting dates, is rejected as ambiguous), start time (am/pm or 24-hour with minutes; a bare hour is ambiguous), end time or duration, IANA timezone from the text (falling back to the profile timezone with a disclosed `timezone_from_profile` reason code — the same convention every other calendar payload already uses), and attendees (explicit addresses in the text, plus the sender when the text asks for it: "add my email address as the attendee", "invite me"). **Nothing is guessed**: every unstated field lands in `missing` and the extraction is not executable.
- **`detect_schedule_requests`** (`detectors.py`) + new `SignalType.schedule_request`: inbox, non-bulk emails only. A complete, future extraction yields confidence 0.9 with `due_at` = event start; anything incomplete or in the past yields confidence 0.45 — below the composition threshold, surfacing in the brief's low-confidence-review section as a visible, non-executable clarification signal (skill §9.1: degraded, never guessed). Deliberately distinct from the generic `request` signal: "please schedule" is scheduling with extraction requirements, never merely a reply-draft prompt, and scheduling evidence is excluded from `detect_deadlines`' double-reporting.
- **`_scheduled_event_candidate`** (`proposal_composition.py`): re-runs the same extractor over the evidence email (title + stored 280-char preview — extraction provably works on what is persisted, not the unstored full body) and composes a `CalendarEventCreatePayload` only from a complete, future extraction. Duplicate guard: if the user's synced calendar already holds an event with the same title and start instant, the candidate is skipped with a distinct `existing_event_duplicate` reason code instead of preparing a duplicate.
- Everything downstream is **unchanged**: origin fingerprint, one-active-per-type walk (D36), approval binding (D29/D30), execution-context resolution (Gmail evidence from a connected Google account resolves `real` mode with the `calendar.events` scope via the existing `source_account_id` binding), policy checks, executor, audit.

Stage 7 has no LLM email extraction by design; the closed cue set is the deterministic floor, and the documented limitation is that scheduling details must appear within the subject + stored body preview — up to 280 characters in demo mode, but on a real account the preview is Gmail's own snippet, measured live at ≈200 characters (round 6b): a real scheduling email must state everything in one compact opening sentence.

### D40 — Independently-verified Calendar event content (deep-review finding, D17 parity)

The Calendar executor verified a create from `insert_event`'s **own response**, and only `summary` + attendees — never start/end, and never an independent read (the ADR's verification decision had promised start/end/attendees/summary). Fixed to full parity with Gmail's D17: `CalendarEventClient` gains `get_event` (a read; the write surface is unchanged — the structural no-update/patch/delete guarantee still holds and is still asserted structurally), and `GoogleCalendarEventExecutor` now re-fetches the created event and verifies: not `cancelled`, exact title, **start/end compared as instants** (Google normalises times to the calendar's offset — `+01:00` for a Europe/London summer event — so comparison is by instant, never by spelling; a naive/all-day value fails closed), and attendees (every approved attendee present; the only tolerated extra is the calendar owner, whom Google may add on its own — any other extra is a mismatch). Any re-fetch failure or mismatch after a successful insert is `uncertain` — the write happened but could not be confirmed — never `failed`, never retried automatically. A 4xx on the insert itself remains a final error (nothing was written).

### D41 — The "(proposed)" placeholder convention is demo-only; solo-event visibility is disclosed (deep-review finding)

Two truthfulness corrections from the same review:

- **Demo-path gating.** On a real account, the "(proposed)" placeholder route would compose a proposal that creates a **near-duplicate sibling** of the user's own placeholder event (same content, title minus " (proposed)", placeholder never modified — no write path exists to transform it, by design). `_proposed_placeholder_candidate` therefore now refuses evidence belonging to a connected Google account (`google_account_ids` threaded from `generate_from_brief`); the demo dataset (synthetic accounts) is unaffected. The convention is now explicitly what it always actually was: a demo fixture, not a product mechanism.
- **Solo-event disclosure.** `detect_meetings` requires ≥ 2 attendees, so a synced solo event (appointment, focus block) never reaches "Today and upcoming" — previously with no disclosure anywhere, which repeatedly read as a sync failure during live testing. The brief now carries a calm `calendar_events_not_listed` notice ("N synced calendar event(s) with fewer than two attendees are not listed under Today and upcoming. They synced correctly and your calendar is unchanged.") counting future, timed, sub-2-attendee events. Widening Today to include solo events is recorded as pilot-readiness debt, not smuggled into this remediation.

### D42 — List-Unsubscribe marks bulk mail (real sandbox finding, round 6)

A live test on 2026-07-21 showed a real promotional email (`temu@eu.temuemail.com`) winning the one active `create_gmail_draft` slot over the user's genuine request: the sender's local part isn't in the closed `_BULK_SENDER_LOCALS` set and "unsubscribe" didn't appear within the stored 280-character preview, so the promo composed a request signal, ranked above the genuine email (frequent-sender relationship boost), and — per the one-active-proposal-per-type policy — blocked the genuine proposal until the user manually rejected it.

Decision: detect bulk mail by the RFC 2369/8058 **`List-Unsubscribe` header** — the standard marker virtually all bulk/marketing mail carries — rather than growing sender/domain blocklists (whack-a-mole) or lifting the one-active-slot policy (which would have surfaced *more* junk proposals, not fewer). Implementation: `GmailDraftClient.get_message` adds `List-Unsubscribe` to its metadata header allow-list (its value is a fact about the message; metadata-only minimisation is unchanged); `EmailMessage` gains `list_unsubscribe: bool = False` (synthetic connector untouched); the flag is persisted in `SourceItem.metadata_json` at normalisation; `is_bulk_email` treats it as bulk alongside the existing local-part and "unsubscribe"-in-preview rules — so no detector (request, scheduling, deadline) ever composes a signal from flagged mail. Messages synced before this change keep their stored metadata (the flag applies to newly-synced mail); the affected historical proposals were already terminal.

The one-active-proposal-per-action-type policy itself is deliberately unchanged: with junk excluded at the source, the slot goes to genuine mail, which is the actual defect the live test exposed.

### Test-clock note (round 6): wall-clock-facing suites must not seed from the frozen reference

Fixing D42's regression run surfaced a latent test-rot defect: the route-level integration suites (`test_google_route_integration`, `test_execution_context_binding` scenario 1) seeded proposals with the frozen `tests/helpers.REFERENCE` (2026-07-15) but approve/execute through the **real app**, whose policy engine checks expiry and event start against `datetime.now(UTC)` — giving every seeded proposal a fixed absolute expiry (2026-07-22) after which the whole suite would silently start failing, regardless of code correctness. Fixed by anchoring exactly those suites to the wall clock (`demo_source_items(anchor=...)`, `scheduling_email_source(reference=...)` — whose event date is now written dynamically, eight days after its reference, weekday matched); every suite that validates with a frozen `now_factory` keeps the frozen reference and its deterministic absolute-date assertions. Documented in `tests/helpers.py`'s module docstring as the two-clock rule.

### D43 — Configured credentials do not authorise OAuth initiation (Stage 11A Phase 4C)

The disposable owner-test environment uses one physical web client for the existing two logical flows. The OIDC and connector routes, state purposes, redirect fields, and requested scope sets remain distinct; only the physical client ID/secret mapping is shared. This Phase 4C mapping supersedes Phase 4B's earlier two-client operational proposal without weakening flow separation.

`GOOGLE_OAUTH_ENABLED=true` now means only that the integration is completely configured. A separate default-false `GOOGLE_OAUTH_INITIATION_ENABLED` gate covers both initiation and both callback routes before state creation/consumption, redirect construction, code exchange, token storage, or account binding. Enabling initiation while the integration itself is disabled fails startup. This is a connection-authorisation boundary, not a production bypass: existing OAuth logic is unchanged behind it, tests explicitly enable it only where they exercise the flow, and demo/synthetic mode remains available while it is false.

Phase 4C installs the client but leaves the gate false. OAuth consent, connection, tokens, provider reads/writes, and soak remain separately authorised future actions.

**Addendum — D43 superseded by D-6A-01 (Stage 11A Phase 6A, dated 2026-08-05):** the single shared `GOOGLE_OAUTH_INITIATION_ENABLED` gate above was a real, exploitable coupling, not a theoretical one. During Stage 11A Phase 6, the project owner enabled it to authorise a connector-consent reconnection; because the gate covered both routes, it also armed OIDC sign-in, and a real (contained, Account-A-only, no personal data) sign-in was completed as a side effect. `GOOGLE_OAUTH_INITIATION_ENABLED` is replaced outright — not deprecated alongside a fallback — by two independent flags, `GOOGLE_OIDC_SIGNIN_ENABLED` and `GOOGLE_CONNECTOR_OAUTH_ENABLED`, each gating exactly one flow's initiation and callback routes; enabling one is structurally never sufficient to enable the other (`oauth_initiation.py`'s two separate guard functions, `require_google_oidc_signin`/`require_google_connector_oauth`). `GOOGLE_OAUTH_ENABLED` remains the same master configuration-completeness prerequisite it always was — never sole authorisation for either flow. The OAuth *state* isolation this ADR already described (distinct purposes, redirect fields, scope sets) was independently reconfirmed to already prevent cross-flow state substitution before this fix — the actual defect was solely at the initiation-gating layer, not the state layer. See [stage-11a-phase-6a-plan.md](../../delivery/stage-11a-phase-6a-plan.md) and [docs/evaluation/stage-11/owner-validation/phase-6a/](../../evaluation/stage-11/owner-validation/phase-6a/) for the full evidence pack.

- Two extra environment-variable groups to configure in production (OIDC client, connector client) — documented in `.env.example`, both empty/false by default, never blocking demo mode or CI.
